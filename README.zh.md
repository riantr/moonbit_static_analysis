# moonbit_static_analysis

[English](README.md) | **中文**

`riantr/moonbit_static_analysis` —— 一个 **三鉴（结构 / 类型 / 行为）静态分析流水线**，
面向 MoonBit。一套基础设施，两种用途：

1. **程序代码修订** —— 分析 **快速进化中的 MoonBit 语言** 写的程序（未定义名、未用绑定、
   类型不匹配、死分支、不可达代码）；
2. **静态状态修订** —— 面向多层状态机的通用机器表审计（`src/statecheck`）：**被审计的主体
   调用本模块**，把它的机器表当纯数据喂进来。

它能读 MoonBit 工具链的每一种文件后缀 —— `.mbt` / `.mbtx` / `.mbti` / `.mbt.md` /
`.mbtp` —— 而且 **绝不修改被扫描的目标**：被分析的仓库既不依赖本模块，也不会被本模块改动。

在 `moonbitlang/core`（1766 个文件）上的实测：**解析 1705 个，actionable 30 条**——其中 10 条
是本前端读不到的构造或算不出来的运算符，另外 20 条是 `MSA-015` 声明上的死存储：一个在任何
读取之前就被覆盖掉的 `let`。那是**被分析代码里的死重量**，不是阅读器的盲区，而且这 20 条每
一条都对着它指名的源码核过。0.4.38 降级的那 12 条——分析器解不出来的名字——算作 notice，
不在这 30 条里。同一棵树上 `moon check --target all` **一条**诊断也不报。

## 特性

- ✅ **三鉴，一份报告** —— 结构遍历 → 类型/符号 → 抽象解释，合并之后一个缺陷就是 **一条**
  发现，它的透镜标签是所有看见它的透镜的并集。合并是无损的：合并前后的计数都保留。
- ✅ **MoonBit 的每一种文件后缀** —— `.mbt` / `.mbtx` / `.mbti` / `.mbt.md` / `.mbtp`，
  其中包括编译器**根本不审**的三种。
- ✅ **只读，不写** —— 被分析的仓库既不依赖本模块，也不会被本模块改动。本工具只在扫描时
  **读取**目标的文件。
- ✅ **跨文件符号解析** —— `--extern-iface-dir` 索引 `.mbti` 里的声明，于是从别的包用来的
  类型不会被报成未定义。
- ✅ **诚实的覆盖率** —— 前端读不完的文件被标成 `PARTIAL`，它边界之后的发现**被计数、
  但不展示**。
- ✅ **只有可能要紧的 notice 才占一行** —— 只有可能藏住发现的 notice 才逐行打印，其余按形状
  汇总成一张表。`--show-notices` 把完整列表带回来。
- ✅ **状态机审计** —— 同一套三鉴跑在纯数据的机器表上：状态即绑定、驱动槽即类型契约、
  历程即抽象执行。
- ✅ **Mermaid 图输出** —— `--mmd` / `--mmd-auto`，可选开启；被截断的图会在自己的头部
  里写明这一点。
- ✅ **文件名里带出处** —— 包、版本、**工具链**和时间戳，好让一次扫描可以和后来的扫描
  互相比较。
- ⚠️ **`--per-function`** —— 行为透镜的第二个入口。用它的数字之前，请先读
  [覆盖范围与边界](#覆盖范围与边界)。

### 宿主要满足什么

发布出去的 wasm **不是自包含的**。它从 `moonbitlang/async` 导入**一组符号**——文件 IO、
进程调用、事件循环——实例化模块时**宿主**必须把这些符号全都提供出来。`moonx` 提供的是
**你的** MoonBit 工具链自带的那个异步运行时。

**这个集合是量出来的，不是一句声明，而且它是下限而不是镜像。** 发布出去的 0.5.4 产物导入了
**92** 个符号；**同一份源码**在本机构建出来（对着本机现在的工具链）的也是 **92** 个——而契约是
**93**，比两者各宽一个，因为一条下限必须同时罩住「旧构建产出的那份产物」和「这次构建产出的
那一份」。原因是 `moon publish` 上传的是**源码**，wasm 由 mooncakes **在服务端**编译，所以产物
那一份确切的导入集合属于 registry 的构建器工具链，而不属于这个仓库——而两个构建器并不总是
一致：对着 core 0.10.20，本地那份要的是 `thread_pool/make_open_stat_job`，而发布出去的那份要的是
`thread_pool/make_openat_job`。门禁检查的是产物的导入集合是契约的**子集**——契约**之外**的符号
是失败（那才是会坑掉用户的方向），契约**之内**而某一次构建没有要的符号只是一条注记。

所以这个产物有一条**下限**，而下限是**工具链**的属性——而发布出去的**字节**必须落在它里面：

| 是什么 | 在哪里 |
|---|---|
| 宿主要能提供的符号——那个**下限** | `_verify/host_requirements.txt` |
| 把产物按这份清单卡住的门 | `_verify/check_host_requirements.ps1` |
| 对**发布出去的字节**做同一件事 | `_verify/selfscan_published.ps1` |

**从 0.4.45 起，运行时来自 `moonbitlang/core/async`——你的工具链自带的那一份——而这个包
本身一个依赖都没有了。** `moon.mod` 里没有 import 块，没有版本需要和用户的工具链对齐。
这正是要点：正是「这个包钉的版本」和「用户的工具链自带的版本」之间的分歧，让 0.4.38
坏掉了。

**宿主 ABI 的模块名没变，变的是符号集合，而且变大了。** wasm 导入的模块名来自源码里的
FFI 声明，而 `moonbitlang/core/async` 仍然用 `moonbitlang/async` 这个名字声明它的宿主
extern——所以宿主提供的还是同一个模块。变的是集合：**90 → 93**，而契约现在是 **93**——那个同时
伺候本地构建和发布构建的**下限**。

| | 符号 |
|---|---|
| **新增** | `stdio/get_stdio_handle`、`thread_pool/get_read_console_result`、`thread_pool/make_read_console_job`、`thread_pool/make_write_console_job`、`thread_pool/run_job` |
| **消失** | `io/errno_is_read_EOF/windows`、`thread_pool/errno_is_cancelled` |

**而下限也跟着抬高了，这一条值得读两遍。** 实测：独立的 `moonbitlang/async` 0.22.5 只能覆盖
93 个里的 **89** 个——它有 `stdio/get_stdio_handle`，但四个 `thread_pool` 新增的一个都没有。
工具链自带的 `moonbitlang/core` **0.10.21+06da1ed44** 声明了 213 个 extern，93 个全覆盖。所以：

> **0.4.45 及以后需要自带 `moonbitlang/core` 0.10.21+06da1ed44（或更新）的 MoonBit 工具链**——
> 也就是 moon 0.1.20261117 或更新。还在自带独立 `moonbitlang/async` 的工具链无法实例化
> 这个产物，而只升级这个包本身改变不了这一点：导入面是发布出去的字节的属性。

**而下限在 2026-11-20 又动了一次，因为工具链动了。** 实测：本机自带的 core 从
`0.10.20+65efd5b93` 换成了 `0.10.21+06da1ed44`（moon `0.1.20261117`），这个仓库一个字节都没改
——是工具链自己更新的。门禁用它自己的话说了这件事的后果：*下限和工具链是同一个事实，工具链
动了，下限就得跟着动*。于是下限动了，**而且带走了一个符号**：core 0.10.21 声明的是
`thread_pool/make_openat_job`，而 0.10.20 声明的是 `thread_pool/make_open_stat_job`，新工具链
**没有**任何宿主提供得了旧名字——所以契约是 **93** 个符号，不是 94 个。一条点名了没有宿主
提供得了的符号的下限，是会坑掉用户的下限，而那正是门禁当成失败的那个方向。

错误在分析器一行都还没跑的时候就到了：

```
LinkError: WebAssembly.Instance(): Import #5 "moonbitlang/async" "thread_pool/make_write_console_job": function import requires a callable
```

**0.4.38 是按比多数人更新的宿主构建的，然后被一个用户撞出来了。** 它的 `moonbitlang/async`
被升到了 0.22.6，而 0.22.6 多声明了三个必须由宿主提供的符号——同样那三个 console job。
自带 0.22.5 的工具链提供不出它们。0.4.45 又要了那三个，外加两个新的，因为它用的运行时
就是随工具链一起发的那一个。如果你是在 0.4.38 上撞到了这个错误：先用 **0.4.37**，或者升级
你的 MoonBit 工具链，或者换到 **0.5.3**。

升级前还有一件事要知道：`moonbitlang/core/async` 目前仍被 core 团队标为 **experimental**，
所以用到它的那些包在自己的 `moon.pkg` 里明确写了出来。随工具链一起发、但还没稳定——这
两件事同时成立，这个包就是两件事都占。

## 快速上手

### 扫描另一个项目 —— 不引入依赖，也不改动它

```bash
moonx riantr/moonbit_static_analysis@latest riantr/moonbit_doubleML@latest
```

`moonx` 下载 mooncakes 为该发布版本构建好的 **预编译 wasm**，缓存后用 `moonrun` 跑起来
——不用 clone，也不用本地构建。

目标可以是注册表坐标（`author/module`，可带 `@version` 或 `@latest`），也可以是本地路径；
省略则扫描当前目录。坐标会先由 `moon fetch` 落到 `.repos/`，然后再遍历。

### 当作库来用

```moonbit
// 用途一：修订一段 MoonBit（当前子集）程序
let result : @pipeline.PipelineResult =
  @pipeline.run(source, "main.mbt", @core.IfaceSymTab::empty())
println(@pipeline.render_result(result))

// 用途二：审计一台状态机（机器表以纯数据进来）
let spec : @statecheck.MachineSpec = { name: "主体", states: [...], ... }
println(@statecheck.render(spec))
```

### 跑一遍 demo

```bash
moon run src/cli          # 6 个样例 × 三鉴、文件种类 demo、样例机器
```

## 用途一：程序代码修订

三鉴是这样装配的：**后面每一鉴都消费前面那一鉴的表**。

| 透镜 | 包 | 职责 | 产出 |
|---|---|---|---|
| 结构 | `src/walk` | 以赋值论绑定、未用/未定义/形参被改、常量折叠剪枝 | 绑定表 `fn_bindings` |
| 类型 | `src/types` | 以标注论契约、推导、赋值/实参/条件检查（**声明来自绑定表**） | 签名表 `sigs` |
| 行为 | `src/interp` | 在格上做抽象解释、按签名分派方法、虚拟栈（**方法表来自签名表**） | 行为发现 |
| 合并 | `src/pipeline` | 一个缺陷在多鉴里的回声 → 一条报告，透镜取并集 | `render_result` |

```
=== undefined.mbt ===
2:10 - error: undefined variable 'missing' (UndefinedName) [structural+type+behavior]
  in main() at undefined.mbt:4
  in g at undefined.mbt:1
Summary: 1 finding(s) (before merge: structural 1, type 2, behavior 1)
```

三鉴都看见的同一个缺陷 → **一条**报告，标签取并集。死分支会被剪两次（结构侧的 `const_eval`
加上行为侧的 `ABool` 格值），而调用一个不存在的 `typo_fn` 产生零条发现。

## 用途二：静态状态修订

`src/statecheck` 接受 **任意状态机的纯数据规格** —— 一个 `MachineSpec`（状态 / 初始 /
终止 / 迁移 / 触发槽落位 / Block 理由 / 历程）。三鉴读机器表的方式，和读程序一模一样：

| 透镜 | 机器侧语义 | 它检查什么 |
|---|---|---|
| 结构 | **状态即绑定**（「以赋值论绑定」抬升到机器表） | 每个状态至少被一条迁移绑定（入或出）；只出不进 → `never entered`；从初始位出发的可达闭包；终止位必须可达——这台机器得能走到头 |
| 类型 | **驱动槽契约**（「以标注论契约」） | 每个触发必须落进已知槽，不许有空槽；一个 `Block` 必须带理由——**无路的一步必须出声说，不能沉默** |
| 行为 | **历程即抽象执行**（虚拟栈） | 每个历程步骤都必须被某条迁移承载；一个搁浅的步骤会带着虚拟栈从入口帧走到错误帧 |

```moonbit
let spec : @statecheck.MachineSpec = { name: "主体", states: [...], ... }
let findings : Array[@report.Report] = @statecheck.audit(spec)
let text : String = @statecheck.render(spec)   // 合并后的文本报告
```

**pyroduct 是被审计的主体，不是依赖**：本模块不依赖 pyroduct；方向是 pyroduct（它的
`audit` 包）拿自己的真实机器表拼出 `MachineSpec` 来调用本模块。单向：机器 → 分析器。

pyroduct 的真实自审（`moon run cmd/main -- audit`）打印：

```
规格 | 计数
---|---
状态 | 034
迁移 | 053
触发→槽 | 049 → 8
无路组合（带理由） | 228
修习历程 | 031 站

未预期发现：**0 条**
```

「未预期发现 0 条」这一行是绊线：真实表上一旦出现新的结构/类型/行为发现，就会让
pyroduct 的测试挂掉，强制一次复审。同一次运行还会列出它**每次都报**的四条**已知设计**
发现（两个只出不进的状态）——上面把它们略去了，因为那是模型本身、不是缺陷，而且要紧的
是最后那一行。

> `moon run src/cli` 末尾打印的 `pyroduct-shaped sample machine` 是本模块自己的
> **8 状态玩具**（`statecheck.pyroduct_flavored()`），不是 pyroduct 的真实表。它带的
> `182:12` 这样的坐标是**由状态名散列出来的稳定伪位置**，不是任何源文件里的行号。

## API 参考

### 程序分析 —— `src/pipeline`

| 函数 | 签名 |
|---|---|
| `run` | `(src : String, file : String, extern_iface : @core.IfaceSymTab) -> PipelineResult` |
| `run_functions` | `(src : String, file : String, extern_iface : @core.IfaceSymTab) -> PipelineResult` |
| `render_result` | `(r : PipelineResult) -> String` |
| `merge_findings` | `(all : Array[@report.Report]) -> Array[@report.Report]` |
| `merge_group` | `(g : Array[@report.Report]) -> @report.Report` |

`run` 让行为透镜在 **模块** 上入口，`run_functions` 让它在每个 **函数** 上入口（见
[覆盖范围与边界](#覆盖范围与边界)）。两个视图是**分开的，不是相加的**。

### 机器表 —— `src/statecheck`

| 函数 | 签名 |
|---|---|
| `audit` | `(spec : MachineSpec) -> Array[@report.Report]` |
| `render` | `(spec : MachineSpec) -> String` |
| `pyroduct_flavored` | `() -> MachineSpec` —— 那个 8 状态样例机器 |

### 图与出处 —— `src/sa`

| 函数 | 签名 |
|---|---|
| `mermaid_states` | `(verdicts : Array[Verdict], summary : Summary, prov : ScanProvenance, per_file : Int32, max_files : Int32) -> String` |
| `provenance_for` | `async (target : String, root : String) -> ScanProvenance` |
| `scan_artifact_name` | `(p : ScanProvenance, root : String) -> String` |
| `aggregate` | `(verdicts : Array[Verdict]) -> Summary` |
| `stamp_utc` | `(ms : Int64) -> String` |
| `moon_mod_version` | `(src : String) -> String` |

`mermaid_states` 返回合法的 mermaid `stateDiagram-v2`。它绕开的两条约束都是实测的，不是
假设的：转移标签是**第一个** `:` 之后的全部内容，所以里面不能再有 `:`——于是位置和消息
都放进带引号的状态标签里；而 MoonBit 没有运算符续行，所以以 `+` 开头的源码行是解析错误，
这就是文档一行一行 `write_string` 写出来的原因。

`per_file` 和 `max_files` 给绘图封顶，`0` 表示不封。**被封顶砍掉的部分会在图里写明**，
写在头部和文件上的一条注里，所以被截断的图不会被读成干净的图。文件按 **actionable**
条数降序排，而不是按原始发现数：在 `moonbitlang/core` 上，原始发现最多的文件是
`v128/simd_float.mbt`，**51** 条发现——全是 notice、零缺陷；按原始数排会把它放在一张
「该把注意力放在哪」为职责的图的第一位。

### 出处 —— 产物的文件名

一次扫描结果是对**某棵特定的树**、被**某个特定的工具链**、在**某个特定的时刻**读出来的
主张。这三样都进文件名 —— `<package>_<version>_<moonbit>_<stamp>.mmd`：

```
moonbit_static_analysis_0.5.4_0.1.20261023_20261024T060000Z.mmd
moonbitlang-core_0.1.20261105+65efd5b93_0.1.20261104_20261114T060000Z.mmd
tree_unknown_unknown_0.1.20261104_20261114T055946Z.mmd     # 版本没定下来
```

| 字段 | 回答什么问题 | 来源 |
|---|---|---|
| `package` | 读的是谁 | 坐标，或**解析后**的目录名 |
| `version` | 它的哪一版 | 目标的 `moon.mod`（`moon.mod.json` 也认） |
| `moonbit` | **是哪个工具链读的** | `moon version`，作为子进程跑 |
| `stamp` | 什么时候 | `@async.now()`，UTC |

`moonbit` 是从树里**恢复不出来**的那一格，也正是它决定一次扫描能不能和后来的扫描比较。
如果 `moon version` 子进程失败，这一格读作 `unknown`，而不是写错。

它刻意**不**做三件事：不省略它定不下来的东西（缺失的版本、工具链或时钟写成字面量
`unknown`——四个字段里省掉一段会让**其余几段错位**）；不产出点开头的文件名（以 `.` 开头的
名字在 `ls` 里看不见，而一个没人能列出来的产物，谁也不会再找到它）；不把文件名本身当成
记录——同样的三件事会以 `%%` 头注释在文档**里面**再写一遍，因为文件会被改名，而一旦改了名，
名字就不再是任何证据。

### 报告 —— `src/report`

| 函数 | 签名 |
|---|---|
| `Report::render` | `(self : Report) -> String` |
| `render_reports` | `(reports : Array[Report]) -> String` |

每条发现都带一条注，含 `WHY:`（哪条规则触发的、依据什么触发的）和 `HOW:`（该改什么），
取自 `@core.Family::advice`。

| 旗标 | 含义 |
|---|---|
| `<target>` | 注册表坐标（`author/module[@version]`）或路径。省略则扫描当前目录。 |
| `--exclude <dir>` | 要跳过的目录名。可重复。它存在是因为点目录规则抓不全：项目可能把 vendored 的注册表快照放在一个普通名字下。 |
| `--extern-iface-dir <dir>` | 在这个目录里找 `.mbti`，把里面声明的类型/值当成被分析的所有 `.mbt` 文件里的合法名字。可重复。最自然的目标是 `moon fetch` 过依赖之后的 `.repos/`。目标自己的树永远被索引。 |
| `--no-auto-fetch-deps` | 默认会读目标的 `moon.mod` 并 `moon fetch` 每个直接依赖。加上它就跳过自动 fetch。 |
| `--mmd <path>` | **同时**把这次扫描写成 mermaid `stateDiagram-v2` 落到 `<path>`，并在最后一行打印 `MMD<TAB><path>`。刻意做成可选：stdout 始终是权威的文本报告。 |
| `--mmd-auto` | 同上，但自己取名，写到**工作目录**——绝不写进被分析的树里。 |
| `--per-function` | 让行为透镜在每个 **函数** 上入口，而不是在模块上。 |
| `--findings-shown-per-file N` | 每个文件**打印**多少条发现（默认 40）。这是打印上限，不是分析上限：SUMMARY 的计数来自全部发现，所以调大它只是把本来已经计数的发现显示出来，不会改动 SUMMARY 里的任何数字。 |
| `--show-notices` | **每一条** notice 都逐行打印，而不只是那些可能藏住一条发现的。默认只有当 notice 所在的区域落在某个函数体的范围内——也就是某个结论可能因为它而被压下——才逐行打印；其余的 notice 按形状汇总进扫描末尾的一张 `NOTICES` 表。这个开关把完整的逐行列表恢复回来，也就是 0.4.36 之前的样子，而且它不改动任何计数：两种模式下 SUMMARY 的数字完全一样。 |
| `--families MSA-007,MSA-002` | 只报这些家族，按它们的**稳定 id**。id 就是每条渲染出的发现、每条 JSON 记录都带的 `MSA-NNN` 码；完整名单见[置信度、id、profile 与 `nosec`](#置信度idprofile-与-nosec)。这个版本不认识的 id 只是一条 `WARNING`，扫描照跑——后来版本才加的家族不该让老分析器的 profile 用不了，而打错字该吵出来而不是直接崩掉。 |
| `--exclude-families MSA-007` | 除了这些家族，其余全报。同一套 id 词汇、同一套规则。一个 id **既**被包含**又**被排除是 `ERROR`，扫描根本不跑：这两条规则互相矛盾，谁赢要由扫描器里两个 `if` 的先后决定。 |
| `--honor-nosec` | 认被分析源码里的 `// nosec` 注释：`// nosec` 压掉那一行上的全部发现，`// nosec MSA-007` 只压掉那一行上的那一个家族。**默认关闭**，而这个默认是一个决定而不是遗漏：一个工具会因为被分析源码里的一句注释就不再报某条发现，那它的输出就得先读一遍源码才敢信。一条**什么都没压掉**的 `// nosec` 会被当成一条自己的发现报出来——过期的抑制是源码的事实，而源码正是这工具分析的东西。 |
| `--ssa-cost` | 量一量**静态单赋值**在目标树上要花多少，打印一行 `SSA-COST`：程序定义了多少变量、SSA 会给它们多少个版本、多少个 φ 函数、以及去掉它们需要多少条拷贝。它是一次**查询**而不是扫描——打印完这一行就停，不报任何发现。它量的是讲义自己的那条说法——南京大学 2026 秋季《Intermediate Representation》（`2_IR.pdf`）那一讲的 p.37：「SSA 可能引入太多变量和 φ 函数」——一条不带数字的说法。这一行把**覆盖率**和数字印在一起，因为没有覆盖率的数字只是一半个数字。 || `--contexts` | 在 `SUMMARY` **之后**打印一行 `CONTEXTS`：行为透镜**执行**了多少个函数体（`executions`）、跨多少个不同签名（函数 + 抽象实参）、从多少条调用串到达、有多少签名被多于一条调用串到达、有多少次到达是递归截断、最深调用栈几层。属于 opt-in，理由与 `--metrics` 相同，但它回答的是**另一个**问题：不是"检查了多少"，而是"分析器把它的执行花在哪里"——本代码在每个调用点**重新执行**被调函数体，而不是把它摘要掉（书里 §8.4 的 functional 方法），因此 §8.3 的调用串上界从未被施加，递归截断是唯一的一处上下文合并。 |

`--mmd` 必须带路径，`--mmd-auto` 是另一个写法，这是刻意的：一个可选的值在这里是有歧义的，
因为在 `<target> --mmd <path>` 里，`--mmd` 后面那个词既可能是路径，也可能是第二个没预期的
目标，没法分辨。

> **命令行无法以非零码退出。** MoonBit 在这里可用的包里没有暴露进程退出的入口，所以一个
> 定位不到的目标会打印 `ERROR` 然后仍然退出 0——**调用方必须读输出，而不是读退出码**。

## 输出怎么读

```
SCANNED	107 files under ...\ML\CI
CLEAN	.mbti	unchecked=0	...\CI/pof/pkg.generated.mbti
PARTIAL	.mbt	defects=1	notices=2	unchecked=17	read up to line 36, 57 after it not shown	...\CI/pof/aggregator.mbt
12:3 - notice: ... (UndefinedName) [behavior, MSA-002, low]
PARSED	32/107 files understood (29.9%); 75 more read only up to their first parse error
SUMMARY	files=107	parsed=32	actionable=56	notices=212	unreliable=15759	withheld=6769	unchecked=2841	total=16027	(actionable+notices+unreliable = total; withheld ⊆ unreliable; unchecked calls are not findings)
```

- **`PARSED` 才是头条。** 前端覆盖的是 MoonBit 的一个**子集**，所以它读不懂的部分量的是
  这工具的盲区，不是你的代码。
- **读了一半的文件仍然值得读。** 解析器记下它**真正**失败的那一行；之前的发现照报
  （`PARTIAL`），之后的计入 `unreliable` 且永不展示——那来自一棵已经不对的树，把它当结果
  端上来，就是这个工具当初要根治的那个毛病。
- **被跳过的声明不会挪动这条边界。** 「这个 `test` 块没被分析」不影响后面的代码仍被读到，
  所以这样的文件是 `FOUND`。
- **`actionable` 不含 notice。** 我们选择不分析的声明形式不是你代码的缺陷——而且它也不装成缺陷：
  一条范围限制渲染成 **`notice:`**，不是 `error:`。
- 读不懂的文件**按原因分组**，而不是一行一个。
- **只有可能藏住发现的 notice 才值得占一行。** 0.4.36 起，扫描只在 notice 所在的区域落在某个
  函数体的范围内——也就是某个结论可能因为它而被压下——时才逐行打印它，其余的 notice 按形状
  汇总进扫描末尾的一张 `NOTICES` 表：

```
NOTICES	TOTAL	notices=14157	printed=1754	aggregated=12403	1754 of them are printed per line: the ones that can hide a finding, and the low-confidence ones, which name a place. The other 12403 are counted by shape below
NOTICES	count=8330	test declaration is outside the analyzed subset; its body was not analyzed
```

  表里的 `notices` 就是 SUMMARY 的 `notices`，`printed` 加 `aggregated` 又等于它，而每一行
  加起来等于 `aggregated`：三个数来自三次不同的计算，读者可以据此核对有没有东西在半路上丢掉。
  上面摘出来的是 TOTAL 行和最大的一行；整张表每种形状一行，从大到小排。
  `printed` 这个数说的是**归类**，不是保证这些行都上了屏——每文件 40 条的打印上限对它们照样
  有效，被藏起来的条数写在 `... N more in this file` 那一行里。`--show-notices` 把完整的
  逐行列表恢复回来。
- `actionable + notices + unreliable` = `total`，这一行自己断言。`withheld` 另行报出，但它是
  `unreliable` 的子集，所以故意不参与这个和式。

**跨文件类型符号解析** —— 一个 `.mbt` 用了别的包里声明的类型（比如 `@argparse` 的
`Command`），单文件分析器只看得见自己那个文件，于是会报 `undefined name 'Command'`。
`--extern-iface-dir <dir>`（可重复）在指定目录里找 `.mbti`，把它们声明的类型和值签名
装进一张**跨文件符号表**；结构遍历和类型透镜在报 `FUndefinedName` 之前会先查这张表。

这张表只**抑制**，从不发明合法绑定：表里没有的名字照报。类型命中返回 `TUnknown`；值命中
返回 `TUnknownFn`——一个已知是值、但签名没读的值——于是 `Command(...)` 既不会触发
`FOpMismatch`，也不会拿一个凭空发明的参数个数去检查。查表前会先剥掉 `@pkg.` 前缀：
`.mbti` 里写的是裸名（`pub fn T::m`），使用处必须写 `@pkg.T::m`，所以精确匹配下这两种
拼法永远碰不上，而命名另一个包最常见的写法也就永远打不中。

### 置信度、id、profile 与 `nosec`

0.4.37 起，每条发现都带着**严重度之外的两个事实**，都在原本放透镜标签的那个方括号里：

```
12:3 - notice: no visible binding for 'cmd' (UndefinedName) [structural, MSA-002, low]
```

**置信度说的是透镜检查了多少。** 严重度说的是这条发现**如果是真的**有多糟；置信度说的是分析器
有多确定它是真的——两者互相独立：一条发现可以又严重又不确定，也可以无关紧要却非常确定。一共
三个值，正好是透镜可能处的三种境地：

| 置信度 | 透镜…… | 家族 | 渲染成 |
|---|---|---|---|
| `high` | 手边就有声明、签名或类型 | 其余全部 | 它自己的严重度 |
| `low` | 只在**名字**上推理 | `UndefinedName`（MSA-002）——它没找到的那个绑定，可能在它根本没拿到的某个文件、某个包里 | `notice:` |
| `undecided` | 根本没法判断 | 一条声明出来的范围限制——分析器自己的盲区 | `notice:` |

**0.4.38 起，这条轴开始决定事情。** 分析器站不住脚的发现被**降级**：渲染成 `notice:`，计入
`notices` 而不是 `actionable`。它**没有被藏起来**——家族、稳定 id、置信度、还有读者屏幕上
属于它自己的那一行都还在；变的是标签和桶。一条 `low` 的发现说的是*它没找到的那个绑定可能在
它根本没拿到的某个文件、某个包里*，而 `actionable` 是你应该去看的那张单子。

一条发现**不会**因为不确定就被丢掉。它只是被以更低的置信度报出来——而这正是「沉默读起来像
『没什么可报』」和「一句关于检查了多少的陈述」之间的全部差别。

**id 才是稳定的那个名字。** 家族的公开名字是第二套要手工维护的词汇：原先十一个名字里有五个
不是标签去掉 `F`（`FParse` → `ParseError`、`FAssignType` → `AssignTypeMismatch`、`FArgType`
→ `ArgTypeMismatch`、`FOpMismatch` → `OperatorMismatch`、`FCondBool` → `NonBooleanCond`）。
一个把 `"family": "ArgTypeMismatch"` 写进抑制或 CI 过滤器的消费方，在名字被改的时候**收不到
任何提醒**——因为名字不是契约。而 **id** 只分配一次、**永不重编号**，所以它能活过一次改名：

| id | 家族 | id | 家族 |
|---|---|---|---|
| `MSA-001` | `ParseError` | `MSA-007` | `ArgTypeMismatch` |
| `MSA-002` | `UndefinedName` | `MSA-008` | `OperatorMismatch` |
| `MSA-003` | `UnusedLocal` | `MSA-009` | `MethodError` |
| `MSA-004` | `UnusedParam` | `MSA-010` | `NonBooleanCond` |
| `MSA-005` | `ParamChanged` | `MSA-011` | `Unreachable` |
| `MSA-006` | `AssignTypeMismatch` | `MSA-012` | `StaleNosec` |
| `MSA-013` | `InfeasibleBranch` | `MSA-014` | `RedundantGuard` |
| `MSA-015` | `DeadStore` | `MSA-016` | `DivisionByZero` |
| `MSA-017` | `NegativeIndex` | `MSA-018` | `TaintFlow` |

这些 id 是**手工**分配的——从枚举的位置推导一个 id，会在每次插入之后把后面所有家族重新编号，
而那正是 id 唯一不能做的事——并且 `_verify/check_family_roster.ps1` 会**检查**这张表：每个家族
一个 id、没有 id 被用两次、id 是从 `MSA-001` 起连着的一段，以及反向表（id → 家族）与正向表
严格互逆。写了两遍的数迟早会自己跟自己不一致，而两张表之间的不一致读者是看不见的，所以要用
一道门去比对它们。

**而且这张表现在也和代码对拍**：`MSA-015`（`DeadStore`，死存储家族）整整一个
版本都漏在这张表外面，却没有任何一道门吭声——因为每道门都是把代码里的花名册跟它自己比对，
而这张表只是散文。`_verify/check_readme_links.ps1` 现在会把**两份** README 里的 id 和名字读
出来，断言每张表点名的家族集合就是 `all_families()` 返回的那个集合——于是「代码里有、表里没有」
的家族变成一道**门禁失败**，而不是读者自己要去发现的惊喜。

**`MSA-015` 也管声明。** `let` 就是一次写入，而一个在任何读取之前就被覆盖掉的 `let`，和一个
被覆盖掉的重赋值一样死：`let mut x = 0` 后面接 `x = 1`（中间没有对 `x` 的读），报在**声明那一行**上。
两者靠各自的措辞区分——*the value bound to 'x'* 和 *the value stored in 'x'*——而且声明只有在
这个名字在别处被读过时才报，所以它绝不会和 `MSA-003`（`UnusedLocal`，说法正相反）重复。

**`MSA-016` 和 `MSA-017` 是讲义自己的两个应用，而工具链这两种形状都抓不到。** 这棵树的符号
分析出自的那一页幻灯片标题是 *Static Analysis — An Example*，它点名了一个分析的两个应用：
*「判定给定程序里所有变量的符号（+、− 或 0）」*——*「检查除以零的错误」*、*「检查数组的负下标」*。
这个分析是一个**符号**定义域（`+`、`−`、`0`、`unknown`），而且它回答的方向是**必然**：符号未知的
除数**不报**——工具只在能证明的时候说「这次除法**就是**除以零」，而一句「可能」的崩溃断言就是
一个等着出现的假阳性。

对着编译器实测：`moon check` 跑一份同时装着 `1 / 0`、`10 / y`、`arr[-1]`、`arr[0 - 1]` 和
`arr[0]` 的探针，退出码 0，对这两种形状一个字都不说。所以这里的一条发现**不是**编译器已经说过
的重复项——它是工具链里唯一会说这件事的东西。

两条断言是两个家族，因为它们是关于**不同操作数**的两条断言：`MSA-016` 关于**除数**（`/` 与 `%`——
取余在运行时同样失败；而浮点被除数不是崩溃，所以不报），`MSA-017` 关于**下标**。一行可以同时
带上两者（`a / b[0]`），而只给一个家族的读者就得猜这条发现说的是哪个操作数。

**profile 按 id 选家族**，而且在扫描开始前就被检查过：这个版本不认识的 id 只是一条 `WARNING`，
扫描照跑；一个既被包含又被排除的 id 是 `ERROR`，扫描根本不跑。这个过滤作用在整份发现列表上、
在可信区间切分**之前**，所以 `total`、`unreliable` 和 `notices` 说的都是同一批发现。

**`nosec` 是按行、按家族**的，而且**默认关闭**：

```moonbit
let x = cmd()          // nosec              -- 压掉这一行上的全部发现
let y = cmd()          // nosec MSA-002      -- 只压掉这一行上的那一个家族
```

一条**什么都没压掉**的 `// nosec` 会被当成一条自己的发现报出来——`StaleNosec`，`MSA-012`——
因为过期的抑制是源码里的死重量，也是它当初指的那段代码已经变了的信号。那条过期发现在抑制
**之后**才生成，所以一条空白的 `// nosec` 压不掉关于自己过期的那条警告。

**而且点名的家族必须用 id 点。** 这条注释的语法就是那个记号加上一串家族 id——`MSA-007`、`MSA-002`——
而一个不是 id 的记号根本不属于这条注释。于是有两种文本根本不是抑制：`///` 文档注释里的 `//`
（文档注释是文本，而那段文本通常正是这条语法自己的文档），以及字符串字面量里的 `//`（引号落在
id 上，于是记号后面那个记号不是 id）。在本工具自己的源码上开着 `--honor-nosec` 实测：这两条
规则之前报出**十九**条过期抑制，每一条都是本仓库自己的散文；而带上这两条规则的树报出**零**条——
而且这两条规则一条 notice 都没有移动。

**而且它只够到发现自己所在的那一行，不够到整条语句。** `bandit` 把问题所在行和**上下文**的
行范围并在一起，所以在它那儿，写在多行调用第一行上的 `// nosec` 能压掉三行之后的那个名字。
这里行就是行：写在语句第一行上的 `// nosec` **够不到**下面的名字，而那个名字会在它自己的位置
被报出来。两种写法都实测过——注释放语句第一行时发现仍然被报出来（渲染成 `notice:`，因为
那是分析器解不出来的名字），注释放名字自己那一行时文件是干净的。把这条规则放宽会移动固定的
语料基线，所以它写在这里，而不是悄悄塞进去。

**而且一次**成功**的抑制，在计数里不留任何痕迹。** `bandit` 留着**两个**计数器——空白的算
`nosec`，点名 id 的算 `skipped_tests`——所以读者能看出有多少发现是被源码自己的注释从报告里
拿走的。这里被 `// nosec` 拿掉的发现就是不在了：SUMMARY 数的是剩下的那些，而没有任何地方说
拿走了多少。实测：开着 `--honor-nosec`、两次抑制都生效时，整个输出里没有一处提到抑制。分析器
在**反方向**上是有披露的——它**查不了**的调用会记成 `unchecked`，而不是被悄悄抹平——所以这两半
今天并不对称，这个不对称写在这里，而不是留给读者自己去发现。

**分析器没能检查的调用，也被披露出来。** 类型透镜只有在读到了被调用方的签名时才检查实参个数
和类型；`.mbti` 给的是名字，从来不给参数表，方法的签名根本不在源码里，而 `..` 链式调用就是
换了写法的方法调用。0.4.37 之前，这三种情况工具一声不吭，于是「我没法检查这个」和「这里没
东西可报」是同一份输出——一个既没有发现、又有四百次没检查的调用的文件，打印出来和一个干净
文件一模一样。现在这个数出现在文件自己的判定行（`unchecked=N`）和 `SUMMARY` 上，并且**故意
不参与**那个和式。在七个固定语料上实测：**30,340** 次没检查的调用，对应 **31** 条 actionable 发现。

**而剩下的那部分按原因拆开了，因为那句话点名的两个原因并不是占大头的两个。** `METRICS calls`
报的是 `sites`、`checked` 和 `not-verified`，八个版本里 `not-verified` 旁边那句话说的是**两种**
原因——*被调者不可调用*和*名字没解析出来*。实测（每个文件只放一个构造，基线是一个可检查的
调用）之后，剩下这部分有**五种**原因，而那句话点名的两种是**唯一会报出来**的两种；另外三种
是**哑的**，而它们是大多数：

| 原因 | 本仓库 | 七个语料 | 报吗 |
|---|---:|---:|---|
| 方法调用——这个透镜没有方法的签名 | **3,808** | **21,350** | 哑 |
| 被调者不可调用 | **498** | **7,647** | 报（`MSA-008`） |
| 跨文件的值，签名从来没读过 | **191** | **1,941** | 哑 |
| `..` 链——这个透镜也没有它的签名 | **0** | **104** | 哑 |
| 名字压根没解析出来 | **0** | **16** | 报（`MSA-002`） |
| **剩下部分** | **4,497** | **31,058** | |

所以本仓库这 4,497 个没被验证的调用点里，**88.9 %** 是哑的，语料那 31,058 个里 **75.3 %**
是哑的；而本仓库剩下部分的 **84.7 %** 是老那句话从来没点过的同一个原因——方法调用。七个语料
加上本仓库自己的源码合起来是 **35,555** 个没被验证的调用点，其中 **25,158** 个是方法调用。
老话对它点名的两个类并没有说错——那两个确实是会报出来的——但它对**整体**说错了，而读者无法
分辨剩下那部分里哪一块是哪一块。这个拆分由分析器自己作为 `METRICS unverified-split` 一行
打印出来，它的 `sum` 就是它拆的那个剩余数，所以这一行自证；上面两个数字由发布门禁钉住。

## 覆盖范围与边界

### 这个工具不跟谁竞争

在 `.mbt` 上，本工具 **不与工具链的编译器竞争**：`moon check` 有真正的解析器，读的是**整个**
语言。在同一棵 `moonbitlang/core` 上它**一条**诊断也不报；本工具的 `.mbt`
前端读的是一个 **子集**，解析 **1766 个文件里的 1705 个**（96.5%）；`.mbti` 和 `.mbt.md` 是 100%。

本工具能做而编译器不能做的：编译器**根本不审**的那三种文件——`.mbti`、`.mbt.md`、
`.mbtp`——以及跨包语义。

### 一条 finding 值多少：sound、complete、useful

没有哪个静态分析是精确的。**Rice 定理**说，程序行为的非平凡性质在一般情况下不可判定，
所以任何分析器都必须放弃点什么，唯一的区别是**放弃哪一头**。标准词汇是这样的：

- **sound** —— 不报漏报（false negative）：报出来的都真的存在；
- **complete** —— 不报错报（false positive）：真的存在的都报出来了；
- **useful** —— sound 或 complete 之一，但不可能两者兼得。

**这个工具是有用的，不是完美的，而且它说清了自己站在哪一边。** 它不声称完备：一条 finding
可能是误报，而它读不懂的语言构造会报成 notice，而不是报成缺陷。它也不声称 sound：死代码
那几个家族是对程序控制流与取值的近似做出的判断，而
[`--per-function`](#--per-function让行为透镜在每个函数上入口) 视图自己就写着它「还没有
sound」。它承诺的东西更窄，而且是逐条 finding 承诺的：**分析器自己站不住脚的 finding 会被
渲染成 notice**（见[置信度、id、profile 与 `nosec`](#置信度idprofile-与-nosec)），每条
notice 都写明工具没读懂什么。

本工具的分析所依据的讲义系列是南京大学《静态程序分析》（`1_Intro.pdf`，李樾，2026 秋季）；
讲义地图——课程有哪些份讲义、每份问什么、本仓库把它做在了哪里——见
`_verify/NARRATIVE.md` §0572；而课程用来衡量本仓库的两件事——本仓库实现了课程自己的哪些分析、
框架与本仓库在哪里不一致——见 §0564。

### 前端读过去、但没有分析的构造

每一个它读过去**却没有分析**的声明或表达式形式都会报成一条 notice，而那条 notice 说的是
**工具**，不是你的代码——所以它渲染成 **`notice:`**，一个自己的标签，而不是借来的 `error:`。
在本项目自己的源码上实测（281 个文件，把每个文件 40 条的打印上限放开，所以数的是全部
发现而不是每份文件的前 40 条）：

| notice | 条数 | | notice | 条数 | | 
|---|---:|---|---|---:|---|
| `test` 声明 | 1807 | | `const` 声明 | 7 |
| `if` 表达式 | 101 | | 短 lambda | 8 |
| `struct` 声明 | 121 | | `type` 声明 | 7 |
| 匿名函数字面量 | 48 | | `try` 表达式 | 1 |
| `enum` 声明 | 35 | | | |

去掉其中任何一行，都需要为那个形式做一个 AST 节点，所以它们是**功能**，不是措辞问题。
真正要紧的区别不在措辞，而在**位置**：**158** 条落在某个函数体的范围内，会把那个函数体的
审计整个关掉，所以它们逐行打印；其余 **1977** 条在所有函数体之外，什么也藏不住，于是在
扫描结束时按形状汇总成一张表。

**这个划分来自分析器自己的几何，而不是来自措辞。** 落在函数体范围内的区域在那个函数的洞
列表里，所以帧审计没法判定它可能读到过的绑定；落在所有函数体之外的区域不在任何函数的洞
列表里，所以它什么也藏不住。同一条 `if expression is outside the analyzed subset`，落在函数
体内就打印，落在模块顶层就汇总——所以一条按消息措辞来分的规则，对其中一半一定是错的。

**`match` 表达式那一行没有了**：0.4.34 开始读 `match` 的 arm，arm 是普通代码，它不再是一块
→「读过去但没分析」的区域。

**而这个排除的比例是量出来的，不是假设的。** 上表 `test` 声明那一行最大，它藏的也最多：
`test` 体整个不被分析，所以种在里面的缺陷是隐形的。在六个植入的缺陷上实测——每个都是它
自己家族的那个 fixture 里的同一个缺陷，唯一的区别是这里它坐在 `test` 体里——分析器检出
**0 / 6**。同样这六个缺陷放在 `fn` 体里是 **6 / 6**，十八个家族的整套 fixture 是
**18 / 18**。这个比例由 `_verify/check_blindspot_rate.ps1` 钉住，而且这个钉子不是空的：
它的自测拿一份 fixture 集合的副本，把 `test` 包装拆掉，要求同一批缺陷被检出，而且各自
作为自己的家族被检出——所以门禁绿的意思是「包装把它们藏了」，而不是「分析器看不见它们」。

**而这个排除是工具的，不是语言的。** `moon check`——MoonBit 编译器——**是**分析 `test` 体的：
给一个 `test` 体里带类型错误的文件，编译器会报出来，位置就在体里那一行。所以语言允许这个
分析，编译器也做了。缺口在本工具的解析器上：它**跳过** `test` 体而不是解析它，所以体里根本
没有建 AST——而且这不是一行能改完的，因为本工具的子集要求一个文件**完整解析**之后才报告，
而 `test` 体是解析器从来没建过 AST 的构造。这两个答案都由
`_verify/settle_0616_blindspot_class.ps1` 复现。

### `ParseError`：一个家族，两种含义

`ParseError` 不是一件事。它既覆盖**声明过的范围限制**——分析器读到了某个构造但没有分析
它——也覆盖文件里的**真缺陷**：没闭合的字符串字面量、坏掉的接口行、重复的签名。两者来自
不同的产出方，由一个判定 `Report::is_notice` 分开：渲染器、计数、mermaid 图和 JSON 桥都走
它。**有一个消费方故意不走**：决定哪些 notice 要在读者屏幕上单独占一行的那个切分，问的
是 `Report::is_declared_scope_limit`——所以一条被降级的发现仍然保留自己那一行。

| 它是什么 | 渲染成 | 计入 |
|---|---|---|
| 一条声明过的范围限制 | `notice:` | notice——不进 `actionable` |
| 一条低置信度的发现（0.4.38 起） | `notice:` | notice——不进 `actionable` |
| 文件里的一个真缺陷 | `error:` | actionable |

在七个固定语料和本项目自己的源码上实测（把每个文件 40 条的打印上限放开，所以数的是全部
发现而不是每份文件的前 40 条）：**24,130** 条 notice——每一条声明过的范围限制，加上 0.4.38
降级的那些低置信度发现。扫描自己也这么说：它的 `NOTICES` 表把其中 **4,034** 条算作逐行打印、
**20,096** 条算作汇总，4,034 + 20,096 = 24,130，正好等于渲染出来的 notice 行数——范围限制
和降级的发现加在一起。这个家族的真缺陷会渲染成 `error:`，发布门禁单独数这一类并要求它为零，
而一个都没有。

### 一个区域只让它「可能读到过」的绑定闭嘴

当前端**故意**不分析某个构造时——一个 `match`、一个表达式位置的 `if`、一个 lambda——
文件里就留下一块**区域**。那块区域从来没被读过，所以它可能包含对周围任何在作用域内的
东西的一次读取。分析器以前把这当成整个函数的**一个**结论：函数里任何地方有一块区域，
这个函数框架能下的**所有**结论就全部关掉——于是函数末尾的一个 `match`，会把函数顶部
声明的绑定的「未被使用」结论一起带走。

现在这个结论是**按绑定**下的。一块区域只能触及在区域开始时就已经在作用域内的绑定，
所以声明在该区域范围**之后**的绑定会被判定，而声明在之前的不会。只在区域**内部**被读取
的绑定仍然不会被报出来：那块区域可能读到过它，硬说它没被读过就是在正确代码上造假阳性。

这是实测的，数字值得一读。把「区域关掉」那个开关拿掉之后（`Walker::holes_in` 里的一行，
再和发布版对拍），在七个固定语料和本项目自己的源码上，工具会产出 **701** 条 `UnusedLocal`
和 **1,338** 条 `UnusedParam`（这里的「自己的源码」就是上面那张通知表数的同一个 281 个文件；
`_verify/` 里没有任何被跟踪的源码，所以被排除在外，这一对数字在干净检出上可复现）；
开着的时候，也就是发布版，它只产出其中**一条**：
`moonbit_labeler` 里一个赋值之后从未被读取的局部变量。所以被区域抑制藏起来的是
**700** 条局部变量和 **1,338** 条参数。这次收窄在今天的语料上**一条**也没找回：
那些绑定全都声明在各自区域的**之前**，那块区域仍然可能读到它们。它买到的是：
区域现在是一个绑定一个绑定地判，所以当某块区域被**读懂**时（也就是去分析 `match`
这件事本身），它恢复的是「其他区域够不着的那些绑定」的结论，而不是什么都恢复不了。

这件事没有编译器可以对照：MoonBit 的 `moon check` 根本没有「未使用的局部变量」这条告警
（本项目 `moon.mod` 里关掉的 `0079` 是 *unused derive*），而每一个固定语料都设了
`warn_list: ""`。这条规则由 `_verify/check_frame_audit.ps1` 和
`_verify/mutate_0501.ps1` 守着。

### `UndefinedName` 的两个盲点

两个都是已知的，而且都写在发现自己的注里：

- `#doc(hidden)` 的 API 在任何 `.mbti` 里都不出现，所以无法从依赖的**源码**索引；
- 写成 `@pkg.fn(1, 2)` 的顶层跨包引用，解析器不会把它折成一个可调用的名字，所以即使那个
  包**已经**被索引，它照样会被报出来。

### `--per-function`：让行为透镜在每个函数上入口

`--per-function` 把每个函数都当作程序的入口来分析，形参绑定到按**声明类型**新造的抽象值。
对入口点来说声明类型是唯一站得住的选择：形参的运行期值未知，透镜只能假定声明类型，
不能更多。

两个视图是**分开的，不是相加的**，所以可以互相比较而不会互相遮蔽。默认（模块）视图
不变：同一批语料加不加这个旗标，数字逐字节一致。

> **这个视图还不算可靠，旗标是可选的就是因为这个。** 它由
> `_verify/census_perfunction.ps1` 在**全部七个**固定语料上量，发版门禁**把数字钉住**。
> 现在它报 **47** 条 `actionable`——46 条在 `moonbitlang/core` 上，1 条在
> `moonbit_labeler` 上——而模块视图报 30 条和 1 条。census 自己的分类是：**26** 条是本前端
> 读不到的构造或算不出来的运算符；**20** 条是死存储——一个没人读的值，也是透镜自己对代码的

> 一个语料上报出的第一条真缺陷。

### 数据流框架同时承载两个方向

`src/flow` 里有一个 bot/join/eq 的 Lattice 和四个不动点求解器；三个增量里，
建立在它上面的每个分析都是 **may** 分析：活跃变量是 may 且后向，区间域沿上升链做 widening。
可用表达式是另一个方向——IN[B] = ∩ over P OUT[P]，一个**必须**分析，它的安全答案是
下近似——而它**不需要第二个求解器**：在 (⊤, ∩) 上的必须分析，就是把同一个载体按相反
次序读的 may 分析，所以它给现成求解器传一个 bot 为 ⊤、join 为 ∩ 的格。入口
节点特判为 ∅（程序开始前什么也不可用）；它三种会静默出错的方式——⊥ 播种、漏掉入口特判、
以及 meet 的累加身份元误取 ∅——各自都被 src/flow/avail_test.mbt 里的一行测试钉住。

**还有第四类分析：会「拿掉」一个事实的那种。** 指针分析（`src/flow/pta.mbt`）问的是
一个指针可能指向哪些对象，而框架把这道题承载了两次。流不敏感的那一版——整份程序一张
points-to 关系表——就是源码里写的那一版；流敏感的那一版在**每个程序位置**各留一张表，
并且在写一个指针时**替换**掉它的对象集合，而不是往里并。这是本包里第一个不是 join 的
传递函数，而它仍然是单调的，所以仍然跑在同一个求解器上。它的可靠性建立在指针定义域上：
一个变量旧的绑定是它私有的，而字段指针是按它的**对象**命名的（`o1.f`），所以每个
（对象，字段）对恰好只有一个指针，不可能有别的东西对那个字段持不同意见。
`src/flow/pta_flow_test.mbt` 把来源讲义为一份程序印出来的两张表都钉住（两种读法各一张），
并且检查两个求解器在它上面给出同一个答案。

**还有第五类：一个三元定义域，读在 CFG 上。** 常量传播（`src/flow/cprop.mbt`）问的是每个
程序点上变量的值是多少，它的定义域是三值的：`Undef`（还没有值）、`C(n)`（常量 `n`）和
`Nac`（不是常量）。定义域和规则本来就在这棵树里，**过程间**的那种读法也在——但那一种读法
没有框架：没有可跑的 CFG、没有可求交的汇合点、没有要到达的不动点。
`src/flow/cprop_intra.mbt` 补上的正是讲义说的那个框架（南京大学《Data Flow Analysis --
Foundations》（`5-6_DFA-FD.pdf`）：一个 CFG、每个汇合点上的 meet、以及那个不动点。**没有一行是重写的。**
讲义的四条 meet 规则——`NAC ⊓ v = NAC`、`UNDEF ⊓ v = v`、`c ⊓ c = c`、`c₁ ⊓ c₂ = NAC`——
正是这个定义域早就有的 join；而三条传递规则——`x = c`、`x = y`、`x = y op z`——正是这个模块
早就有的规则，现在由一个函数（`cprop_assign`）供两种读法共用。两种读法只在**一种节点**
上不同：在调用处，过程间的规则给恒等，过程内的规则给 `Nac`。新的是框架，以及跑它的第三个
求解器。

**第三个求解器是另一种形状，不是新算法。** `src/flow/worklist.mbt` 里的 `solve_worklist`
就是讲义 §11 印的那个前向工作表：状态是 `OUT[B]`，每个节点的输入从它的前驱读回来，
而后继只有在它前驱的 OUT 变了时才被重新入队。这个包里本来就有轮转求解器（同一套方程、
不同的访问次序）和一个把状态放在节点**之前**的工作表；这是第三种形状。讲义把工作表称作
「Iterative Algorithm 的一个优化」（p.256），这句话是一个断言——两者算的是**同一个**
不动点——所以有一行测试把常量传播分别跑过新求解器和轮转求解器，要求它们**逐节点**相同；
另有一行测试要求工作表对两个前驱做 **join** 而不是覆盖，因为那正是 meet，也正是工作表
唯一会悄悄做错的事。

**这个分析不是分配的，而树里就是这么写的。** 讲义自己印了反例（p.249-252）：在图
`Entry → X(a=1,b=9) / Y(a=9,b=1) → Z(c=a+b)` 上，先 join 再传递给出 `c = NAC`，先传递再
join 给出 `c = 10`——两种次序里和都是 10，但 meet 已经把常量丢掉了。本树的分析先 join，
所以它给 `NAC`，也就是安全的那一边；而测试把**两种次序都钉住**，于是它们的差别是树里的
一个事实，而不是某页幻灯片上的旁注。定义域的序（`cpv_leq`）是公开的而不是私有的，
因为讲义最后一道题——*「证明我们的常量传播分析是单调的」*（p.254）——是一个关于某个函数
的断言，而那个函数必须够得着才能被测试；单调性也正是不动点定理会用到的前提。

**而它不开新的发现族。** 这道分析本可以报出的那一类——结果在程序跑起来之前就已经定下的
分支——已经由 `MSA-013`（`InfeasibleBranch`）和 `MSA-014`（`RedundantGuard`）说了。所以
`cprop_const_branches` 是一次**测量**，不是一次报告：它点名这道分析能定下哪些分支，而且
它不开新的族，因为本来就能承载那些发现的族已经存在。

**还有第六类：在它之上的整程序那张图。** 调用图（`src/flow/callgraph.mbt`）是讲义的第二
节——南京大学《Interprocedural Analysis》（`7_Inter.pdf`，谭添），p.33-39 与 p.52-56——也是方法调用不再是
一个洞的地方。讲义的 `Resolve(call)` 有三种情形，而 MoonBit 三种都答得上：一次**静态**
调用 `f(x)` 点名了自己的目标；一次**特殊**调用 `Type::m(x)` 在调用里就点了自己的类型；
一次**虚拟**调用 `recv.m(x)` 则由接收者的**声明类型**决定——若那是 trait，目标就是
trait 自己的方法，加上每一个实现了它的类型，也就是讲义那句「c 的子类或 c 自己」；若那是
一个具体类型，目标就是那个类型自己的方法。

MoonBit 没有类，所以讲义的**类层次**就是 **trait 层次**——`impl Trait for Type` 与
`derive(Trait)`——而它是从源码文本里读出来的，因为这棵树的 AST 不带它：parser 把 `trait`
与 `impl` 声明整块读过，于是「哪个类型实现了哪个 trait」在这棵树里曾经是谁也答不出的
问题。接收者的**声明类型**是注解（`SLet` 的第二个字段、`Param.tyann`），因为类型透镜
只公开模块帧，函数内部的局部类型因此根本没有被公开。

两条边界是被**数出来**的，不是被藏起来的。**方法体不在这棵树里**，所以图上的边只是
**点名**那些实现，然后停在那里——一个实现内部的调用是看不见的。而接收者**没有声明
类型**的调用解析不出任何目标，于是被记成未解析，而不是被连到一个猜测上。

**还有第七类：同一个指针问题，换一个上下文、换一个范围来问。** 上面的指针分析回答的是
「这个指针可能指向哪些对象」，而且是在整程序上回答、把所有调用上下文都并成一个答案。
定义这道分析的讲义把这个「并」写成一道**选择题**，而不是事实：《Pointer Analysis》
（`8_PTA.pdf`，南京大学 谭添，2021）p.34 印着 **Key Factors** 表，四个因子里有一行是 *Context
sensitivity ——「如何给调用上下文建模？」—— Context-sensitive | Context-insensitive*；
p.49-53 展开两种读法，p.53 用 *「We start with this」* 标出被合并的那一种。第四行是
*Analysis scope ——「程序的哪些部分该被分析？」—— Whole-program | Demand-driven*，
p.72-77 展开它。所以这棵树留空的那几格是**讲义自己的选项**，其中两格现在建好了。

`src/flow/pta_ctx.mbt` 是上下文敏感的那一版：分析按 **(函数, 上下文)** 对跑，而上下文由
调用点贡献。实现了三种抽象，都是讲义自己的——后续讲义《Pointer Analysis — Context
Sensitivity (I)》（`11-12_PTA-CS.pdf`）p.99-115 印着 `Select` 的几种变体：**不敏感**
（`Select _,_,_ = []`，p.102——每个函数一个状态）、**调用点**（`Select(c,l,_) = [l_1..l_k]`，
p.103——取最后 `k` 个调用点，也就是 k-CFA，Shivers 1991）、以及**对象**（p.100——接收者的
分配点）。**调用点的标号就是行号**，这是讲义自己的标号；一行里有两个调用时用 `line:col`。

**类型敏感现在实现了，而当初没实现的理由依然成立。** `Select` 的第三种变体是接收者的**类型**，
现在有实现了：接收者的**声明类型**读得到——就是接收者绑定时写的那个标注——所以这个变体问的是
这棵树答得上来的问题。仍然读不到的是讲义自己的 `InType`，也就是**包含**分配点的那个类型：
`11-12_PTA-CS.pdf` p.171 对它很强调（*「InType(o3) = X (not Y!)」*），而那个类型是方法体所在的类——
这棵树的 AST 里**没有方法体**，解析器把 `impl`、`trait`、`struct`、`enum` 整块读过去。所以这个变体用
接收者的声明类型：抽象的**种类**是同一个——用类型代替对象——而讲义自己的测量也复现了：三个同类型的
接收者给出**一个**上下文，而对象敏感给出**三个**（p.174）。这里原来写的是「类型敏感没有实现，
因为局部变量的类型在这棵包的任何地方都读不到」；那句话对**推断**出来的类型成立，对**声明**的类型
不成立，而这一版读法就是建在声明类型上的。

`src/flow/pta_demand.mbt` 是按需分析的那一版，它复现的是讲义 p.76 的那一**列**：客户是
*call graph construction*，关心点是讲义那份程序的**第 5 行**（`z.bar()`），答案是
`z ➝ {o4}`。四条规则是**倒着**读的——哪些语句写了这个指针、它们读了什么——所以算出来的
只有**被点名的那几个指针**的表。两条边界是被**数出来**的，不是被藏起来的。这一支里
**调用的结果不是一个源**：没被建模的值贡献为零，而不是贡献一个编出来的对象。而被点名的
**参数**确实跨过调用边界，落到调用者的实参上——否则需求就停在被调函数门口了。

**范围改变的是算多少，不是算成什么。** 对于被点名的那个指针，按需分析给出的就是整程序
分析给出的答案；变的是被计算的那批指针。有一行测试要求这个相等式成立，所以第二种读法
不可能悄悄变成另一道分析。

**而它仍然不开新的发现族。** 两种读法都不报任何东西：上下文和范围都是一次**测量**，而这棵树
的指针分析是库级的，不在报告流水线里。发现族清单是十八个，而它一个也没加。

**还有第八类：同一个指针问题，不要堆地问。** 上面的指针分析问的是「这个指针可能指向哪些
对象」，答案是一组对象，而对象总得被**命名**。storeless 模型不命名它们。讲义自己的
**Heap abstraction** 那一行——*如何给堆内存建模？—— Allocation-site | Storeless*（p.34，
并且在每个因子那节的开头重印：p.48、p.54、p.71，以及 p.78 的「Pointer Analysis in This
Course」）——有第二格，而讲义在 p.42-43 引的就是它的定义：Vini Kanvar 与 Uday P. Khedker，
《Heap Abstractions for Static Analysis》，ACM Computing Surveys 2016（免费全文是
arXiv:1403.4910v5）。讲义点名这格九次、定义它零次；定义在综述里，所以这一格去读综述。

`src/flow/pta_storeless.mbt` 是 storeless 的那一版。堆是一组**访问路径**——一个指针变量后面
跟一串字段名——而综述的定义是精确的：*「storeless 模型不把与这些访问路径对应的内存位置或
对象显式化。设 V 为根变量集合、F 为字段变量名集合，则访问路径集合定义为 V x F*」*（p.7）。
这里的定义域就是那个集合，而规则是 `pta.mbt` 的那四条规则搬到这个定义域上。其中不一样的是
**New**：新的位置由**以变量为根的路径**命名，而不是由分配点命名——因为综述把「分配点」归类为
一种**概括**（p.11），而这一格正是没有概括的那个模型。在这里把新位置写成 `o1` 的树，是分配点
模型穿着 storeless 模型的衣服。

**概括是综述的，而它正是让这个模型有限的东西。** 访问路径集合是 `V x F*`，所以「访问路径的
个数可能是无限的，每条访问路径的长度也无界」（p.7）。综述用 **k-limiting 谓词**来框它——
「堆位置是否距根变量至多 k 次间接？」（p.12）——并配一个自环，它「为超过 k = 2 次间接的访问
路径存下伪别名」（p.9）。这棵树实现了那个谓词，并且**数切点**：比界更深的路径被并进它前缀
的那些位置。切点按**不同的位置**数，而不是按轮数数——不动点每轮把规则应用一遍，所以计数器数到
的是某个切点出现在几轮里，而不是程序里有几个切点。

**而算法是这棵树的，因为综述说了算法不是它的主题。** 它的摘要就是这么说的：*「我们的兴趣
在抽象上，而不在构造这些抽象的算法上」*（p.1）。所以这一格是综述的模型、综述的概括，加上这棵树
自己的那四条规则——而综述的 Figure 6 **没有**被复现，因为复现它的树等于宣称一个综述没有给的
算法。

**两个模型并排，测量。** 同一批程序由两个模型读，别名判定逐对比较。在讲义自己 p.28-29 的
那份程序上，两个模型**一致**——三对、三次一致、零次不一致——因为别名问题在两套词汇里是同一个
问题。而它们对「一个变量可能到达什么」**不一致**，而且这个差别是关于两种**抽象**的事实，不是
关于任一实现的。在 `x = new C(); x = new D(); y = x;` 上，分配点模型说 `x -> {o1,o2}`、
`y -> {o1,o2}`——两个**位置**、两个对象——而 storeless 模型说 `x -> {x}`、`y -> {x}`——一个
**根**、一条路径。这就是综述自己的区分（*「用分配点做概括，会把在同一个程序位置分配出去的堆对象
合并掉」*，p.11），也是两个模型的 points-to 答案不可比、而别名答案可比的原因。

**而这条边界是被数出来的，不是被藏起来的。** 在这套规则里，一个值永远是它所指位置的**根**，
所以最深的值在深度零上，综述里那个伪别名——一个指针到达界以下的路径——根本不会通过指针产生。
它在关系里才看得见：比界更深的路径在那里被并进前缀。两个模型的别名判定由一行测试逐对比较，
而那一行不一致的，就是上面这一行。

**而它仍然不开新的发现族。** 堆抽象是一次**测量**，不是一份报告：这个分析没加任何发现族，
storeless 模型是库级的分析，和另外两种指针读法并列。
**而且是第九种：同一个指针问题，问在指针流图上。** 上面每一种读法都是扫函数的语句，把学到的
东西并进一张表。而给出**方法调用规则**的那份讲义问的是同一个问题，只是问在**图**上。
`9-10_PTA-FD.pdf`（南京大学《Pointer Analysis — Flow and Dispatch》）p.23 印着**指针流图**的
边表——*New: N/A；Assign: x←y；Store: o_i.f←y；Load: y←o_i.f*——p.24-25 印着它自己的例子程序

```
a = b;      ①
c.f = a;    ②
d = c;      ③
c.f = d;    ④
e = d.f;    ⑤
```

带着那句标注 *(o_i ∈ pts(c), o_i ∈ pts(d))*，而 p.33 画出画完的图：**五条**箭头——`b→a`、
`a→o_i.f`、`c→d`、`d→o_i.f`、`o_i.f→e`。不是六条：没有往 `e` 里的存储。

`src/flow/pfg.mbt` 就是那张图，而且按讲义的方式解：一个装着**增量**的工作表
（`Δ = pts – pt(n)`，p.116），它的 `Propagate` 只推增量；`AddEdge` 在有新对象到达一个节点时把
`t, pts(s)` 加进工作表（p.68、p.119）。讲义自己的工作表轨迹被**一步一步**复现——
`b, {o1}; c, {o3}; a, {o1}; d, {o3}; o3.f, {o1}; o3.f, {o3}; e, {o1}; e, {o3}`——八步，就在印着它
的那几页上（p.74、p.76、p.81、p.83、p.88、p.89、p.90）。讲义自己的表也从里面出来：
`a -> {o1}; b -> {o1}; c -> {o3}; d -> {o3}; e -> {o1,o3}; o3.f -> {o1,o3}`。

**而且这张图是和那一种读法**对照**的，不是并排放着。** 一个问题的第二套实现就是它的第二个答案，
所以指针流图那一版跑在同一份程序上，和 `pta_run` 的两张表由一个测试要求**相等**。

**而且同一份讲义的跨过程算法也建起来了，调用图是边走边长出来的。** p.115 说
*「Run together with call graph construction」*、*「Call graph forms a "reachable world"」*、
*「Only reachable methods and statements are analyzed」*，p.116-119 给出 `Solve(main)`、
`AddReachable(m)`、`ProcessCall(x, o_i)` 和 `AddEdge(s, t)` 的伪代码——最后一个正是
*「if s → t ∉ PFG then add s → t to PFG; if pts(s) is not empty then add t, pts(s) to WL」*。
讲义的输出是**两样**东西（p.125）：*「Points-to Relations (pt), Call Graph (CG)」*。

`src/flow/pta_inter.mbt` 就是那个算法，而它的头条是**与另外单独建的调用图不一致**。在讲义自己的
例子上（`A b = new B(); b.foo(a);`，p.126-152），边走边长的那张图说 **`main -> B::foo`**——
分派是按接收者的**对象**做的——而单独建的那张图说 **`main -> A::foo`**，因为它按接收者的
**声明类型**分派（deck 7 的 CHA，p.33-39）。讲义的这个例子就是为了让这个差别看得见而造的，而它
确实看得见。那两张图在一个「唯一的调用点直接点名被调者」的程序上还必须**一致**，所以分歧不会扩散。

**而且上下文敏感的堆是讲义自己的，而且在它自己的表上量。** `11-12_PTA-CS.pdf` p.28-30 把**堆**
也变成一个选择：*「The abstract objects are also qualified by contexts (called heap contexts)」*、
*「The most common choice is to inherit contexts from the method where the object is
allocated」*，而对象自己的名字是 `c: o_i`。p.56 印着**两**列——**「C.I. + C.S. heap」**和
**「C.S. + C.S heap」**——以及**两**条结论：*「Context-sensitive heap improves precision」*和
*「Without C.S., C.S. heap cannot improve precision」*。

`src/flow/pta_heap_ctx.mbt` 就是那一版，而且**两列都逐行复现**。右列：`n1 -> {o1}`、
`n2 -> {o2}`、`3:p -> {o1}`、`3:x -> {3:o8}`、`x1 -> {3:o8}`、`4:p -> {o2}`、`4:x -> {4:o8}`、
`x2 -> {4:o8}`、`n -> {o1}`、`3:o8.f -> {o1}`、`4:o8.f -> {o2}`。左列：`p -> {o1,o2}`、
`x -> {3:o8,4:o8}`、`x1 -> {3:o8,4:o8}`、`x2 -> {3:o8,4:o8}`、`n -> {o1,o2}`、
`3:o8.f -> {o1,o2}`、`4:o8.f -> {o1,o2}`。那两条结论也是测量：上下文敏感的堆把 `n` 从两个对象
变成**一个**（13 对对 14 对），而在上下文不敏感的分析下它**哪儿也去不了**——和普通堆给出的答案
一样，这正是*「Without C.S., C.S. heap cannot improve precision」*的意思。

**而且三种抽象是拿来对照的，不是拿来供选择的。** 同一份讲义把三种变体的上下文并排印着（p.174）：
*「Object-sensitivity: o3, o5, [o7]」*对着*「Type-sensitivity: [X]」*，并给出结论
*「Type sensitivity is a coarser abstraction over object sensitivity」*。这棵树读出的表是同一个：
`call-site: [4, 6, 8] | object: [o3, o5, o7] | type: [Y]`——而合并的代价是量出来的：在类型变体下，
同一个方法的两次调用是**一个**状态，于是形参同时持有两个对象、两个结果相同；而调用点变体和对象
变体把它们分开。

**而且它仍然不开新的发现族。** 一张图、一张边走边长的调用图、一个堆、一个上下文，全都是
**测量**；这棵树的指针分析是库级的，不在报告流水线里。发现族清单是十八个，而它一个也没加。

### 污染数据是一个对象，所以污点分析**就是**指针分析

`src/flow/taint.mbt` 是**安全**那一份讲义的第四章——南京大学田田《Static Analysis for
Security》p.64-85——而 p.70 那一页上的句子决定了它该怎么写：**"Taint and Pointer
Analysis, Together"**。讲义把污染数据当成**对象**（p.71-72：*"Tainted data t_i, t_j ∈ T ⊂
O"*），把源当成一个**分配点**，然后用指针分析**自己**的规则传播污点（p.75）。所以这
**不是第二套指针分析**：它就是这棵树已经有的那套指针分析（`src/flow/pta.mbt`），外加
**每个源调用点一个额外对象**。

**种子就是全部的差别。** 讲义的源规则（p.74）写着 `m ∈ Sources ⇒ t_l ∈ pt(r)`，而讲义
自己的例子把污染数据印在**源调用所绑定的那个变量**的指向集**里面**——`pw → o11, t3`。所以
一个污染数据是按它的**调用点**命名的对象（`t3`，就像分配点被命名成 `o3`），它一开始就在调用
结果的那条指向集里。之后的一切都是讲义的四条规则——New、Assign、Store、Load——它们
`pta.mbt` 早已**只在一个地方**实现，而这个文件是**调用**它们，不是抄一份。

**输出是讲义的那个三元组。** p.73 定义它——*"(i, j, k) = tainted data from call site i may
flow to the k-th argument of call site j"*——而 p.84 印出讲义对自己例子的答案：
**`TaintFlows: { ⟨3, 7, 0⟩ }`**。这个例子是**逐行**复现的：第 2 行的分配是 `o2`，第 3 行的
源调用造出 `t3`，第 4 行的复制共享 `o2`，第 5 行的写和第 6 行的读带着 `t3`，第 7 行的汇
报出讲义自己的三元组。`src/flow/taint_test.mbt` 把这些表逐条钉住。

**和讲义的表有一处差别，而它是量出来的。** 讲义里的 `o11` 是源调用**返回**的那个对象
（`getPassword` 里面第 11 行的 `new String(…)`），而这棵树的指针分析不建模调用的返回值
——所以这里没有 `o11`，`pw` **只**指向那个污染数据。MoonBit 的翻译把字段填上而不是留空，
于是 `o2.f` 还持有字段的初始值。讲义的**答案**——那个三元组——是同一个。

**源和汇是参数，而这就是讲义自己的形状。** p.73 把它们定成分析者提供的两个集合：*"Sources
= a set of source methods"*、*"Sinks = a set of sink methods with sensitive arguments"*。讲义
自己的例子用的是 `getPassword()` 和 `log(String)`——被分析程序自己的两个函数，而且哪一个都
不是任何工具链定义的名字。一套自带源名字表的污点分析回答的是**另一个**问题，所以
`TaintSpec` 带着这两个集合，分析去读它们。

**而这些边界是讲义自己的边界，不是实现偷懒的边界。** 讲义自己说（p.61-62）：*"Explicit
flows generally carry more information than covert channels, so we focus on explicit flows"*
——所以**隐式**流（在被污染数据上的分支、终止信道、计时信道、异常信道）**按讲义自己的决定**
就在范围之外。**安全等级**（p.25-28）和**非干涉性**性质（p.29-36）则是另一个理由：等级是格
上的元素、策略是格上的序，而一条非干涉性的断言是同一个程序在**不同高输入下跑两遍**的**关系
性质**，没有哪个 may 分析能回答它。而这套分析是**过程内**的，因为它所基于的指针分析是每个
函数一张表。

**而且在 0587 里它开了新的发现族。** 污点分析和上面的指针分析一样，是 `src/flow` 里的**库级**
能力：它算出讲义的三元组交给调用方——而**0587** 正是给这些三元组一个属于它们自己的发现族的那个
增量，`MSA-018`（`TaintFlow`）。发现族清单是十八个。

### 到达汇的污染数据是一条发现

`src/pipeline/taintcheck.mbt` 把讲义的三元组变成**发现**，而这个发现族是 **`MSA-018`
（`TaintFlow`）**——清单上的**第十八个**。

**发现坐在汇上。** 汇调用就是读者要去看的那一行，所以发现落在汇所在的行，消息以汇的名字开头：
*the sensitive argument 0 of 'log' may receive tainted data from 'get_password'*。**源**也要被点
名，因为不带源的「污染数据」不是关于程序的事实。

**一个汇调用一条发现，而这是合并造成的。** 流水线把一个发现族在同一**行**上压成一条发现，所以一
个有两个敏感参数的汇会丢掉其中一个，而两个源到达同一个汇会丢掉**其中之一**。所以流在这里按汇
调用**分组**，消息把组里覆盖到的每一个参数、每一个源都写出来——合并就没有东西可压，报告也保住
了整个事实。

**谓词是可检查的**，而且这是这棵树里第一条断言关于**流**而不是关于某个位置的谓词：

```
taint_reaches_sink(sink=log, source=get_password, arg=0, line=7, col=3)
```

**汇**是主语，**源**是数据从哪儿来，**参数**就是讲义自己的 `k`。这些值是消息**自己的词**，所以
检查者按消息读的方式去拆它们。

**规格是读者给的，而它是一个参数。** `--taint-source <fn>` 点名一个结果就是污染数据的函数；
`--taint-sink <fn>:<idx>` 点名一个汇和它那个敏感参数的下标——`log:0` 就是讲义自己的
`<log(String), 0>`。两者都可重复，格式不对的那个被**拒绝**而不是被丢掉（被丢掉的汇会扫完程序什么
都不报，那看起来和一个干净的程序一模一样），没有规格时这个发现族什么都不说——和这棵树里其余
分析一样的诚实默认。

**而那三道闸门是流水线的。** 前端没读完整个的文件、含有它没读过的区域的函数、以及控制流图**丢
了语句**的函数，都是这个发现族不分析的函数——第三道是因为丢掉的那条语句可能是一个**净化器**，
而分析没看见的净化器，就是分析相信、而程序并没有的那条流。


### 讲义自己的注入例子不会被报出来——这是实测的

**这份安全讲义的第二章是*机密性与完整性*，而它那张完整性幻灯片上写的正是整章要讲的形状：**

```
x = readInput();   // untrusted
cmd = "..." + x;
execute(cmd);      // critical (trusted)
```

而 p.41 点名了这个形状是什么：**「注入错误（2013-2019 年漏洞的第一号成因）」**——命令注入、SQL 注入、XSS。

**工具不报它，两种语法形式都不报，而原因是指针分析自己的，不是污点规则有缺口。** 字符串拼接和带
插值的字符串，都是指针分析**不建模**的值——`src/flow/pta.mbt` 用它自己的话说：*「其余一切都
是空的，而这是 sound 的方向」*——所以污染数据进不去派生变量的指向集合，讲义自己的汇规则也就无
从下手。

**这是实测的，而且实测是三行。** 讲义那个程序带拼接，报**零条**；同一个程序带插值，报**零条**；
同一个程序把派生值**去掉**，就报出了那条流。这三个程序只差一个表达式，而报零条的那两个被测试
钉住了。

**而这同时也是讲义自己的规则表。** p.75 列了四条规则——New、Assign、Store、Load——其中没有一条
是关于派生值的。污点分析是指针分析加一颗种子，所以它回答的正好就是那四条规则能回答的。

**这个形状并不罕见。** 在七个固定语料上实测：**827** 处把一个调用的结果带进字符串——**314** 处拼
接、**513** 处插值。这是**语法**计数而不是流计数：其中大多数是无害的（一行日志不是注入），而这
个计数要说的是：这条边界不是理论上的。

**而能关掉它的那一条规则被点了名，因为有名字的边界是一个决定，没有名字的边界是一个借口。** 它
是*「派生自污染数据的值带着污染」*，它属于**污点层**而不属于指针分析——那会让污点分析比讲义的
四条规则**宽一条**。那是对这个工具自身声明的改变，所以它写在这里，而没有被做掉。


### 讲义自己的规则可以被读出来，然后跑起来

《Datalog-Based Program Analysis》（`14_Datalog.pdf`，Tian Tan，南京大学，93 页）第一章讲的是一个抱怨：同一个指针
分析有**命令式**的写法（p.9-14——一个工作表、一个 `Solve(main)` 循环，以及「这么多实现细节」），
也有**声明式**的写法（p.15-16——七条规则，「Succinct / Readable (logic-based specification) /
Easy to implement」）。这份讲义要说的不是 Datalog 是门更好的语言，而是：**规则本身就是规格**，
而能读的规格才是能核对的规格。

`src/flow/datalog.mbt` 与 `src/flow/datalog_parse.mbt` 就是那个引擎和那个读取器，它们的存在是为了
让这句话**可被检验**：讲义自己的规则被写出来、被读回去、被执行，并与本仓库已有的指针分析给出的
答案对照。

**读取器读的是讲义自己的语法，而且是按上下文读的。** 讲义的语法分不出变量和值——它的事实是
`New(b, o1)`（p.65），它的规则是 `VarPointsTo(x, o) <- New(x, o).`（p.70），而**两者**里对象名和
变量都是裸标识符。所以这个区分是**上下文**的：**事实**的裸项是值，**规则**的裸项是变量。一个靠猜的
读取器必然在两种形式里错掉一种，而讲义是故意把两种都印出来的。

**讲义的多头简写是「一个体、三个头」，也就是三条规则共用一个体。** p.15 把三个头写在几行上、共用
一个体，读取器把它展开，因为它本来就是这个意思：

```
VarPointsTo(x, o) <- New(x, o).        // 一个头
FieldPointsTo(f, o) <- New(f, o).      // 讲义 p.15 的写法：三个头、
FieldPointsTo(f, o) <- HeapStore(f, o). // 一个体——读成三条规则
```

**两次拒绝都是拒绝，不是悄悄丢掉。** **不安全**的规则会被拒绝（每个变量都必须至少出现在一个
非取反的关系原子里，p.51-53），**递归与取反没有分开**的程序也会被拒绝（p.54-56）。两者都会给出
指名是哪条规则的诊断，求解返回的是*不成功*而不是一个空答案。空答案和「答案本来就是空的」看起来
一模一样——这正是「工具说不知道」与「工具什么也没说」之间的差别。

**数字是数字，不是文本。** `age >= 18` 必须把 **9** 排在 **18** 之下，而按文本比较会把 `"9"` 排在
`"18"` *之上*，因为 `'9'` 是更大的字符。讲义自己的例子里就有一个九年级学生（p.29、p.32），而这个
例子就是一行被钉住的测试。

**并且引擎是单调的、是会终止的**（p.57-59），因为事实永不被删除，而 IDB 谓词的可能取值是有限的
——这个论证的后半句正好就是上面的规则安全性。递归的轮数是**实测**的，不是断言的：被钉住的那一行
读出的是不动点实际走了几轮。

**而往返才是关键。** 读取器把规则用讲义自己的记法写回去，讲义自己的指针分析规则（p.70）与污点
规则（p.91）**逐字**回来——从文本读入，保持讲义的顺序、讲义的措辞。一个读不回来的规格，不是这个
工具能核对的规格。

**这不是什么。** 它**不是**第二套指针分析。Datalog 引擎算的是讲义的规则；本仓库已有的指针分析在
同一个程序上算的是同一个答案，而接下来的增量会把两者对照着看。一个事实，树上只放一处——所以
Datalog 引擎是讲义的*规格*，`src/flow/pta.mbt` 是本仓库的*实现*，而讲义提出的问题是：这两者在
哪里一致、在哪里不一致。

### 讲义自己的规则可以跑起来，而且能和本仓库已有的答案对拍

这份讲义的主张（p.15-16）不是「Datalog 比工作表快」，而是**规则本身就是规格**——
「Succinct / Readable (logic-based specification) / Easy to implement」——而能读的规格才是
能核对的规格。`src/flow/datalog_pointer.mbt` 把这句话变成**可检验的**：讲义自己的四条规则
（p.70）被写出来，程序里的语句变成讲义自己的 EDB 关系，规则被**执行**，答案与本仓库
`pta_run` 在同一个程序上给出的答案**对拍**。

**规则是文本，不是代码。** 用代码搭出来的规则就是命令式换了张皮；写成文本的规则才能被读、
被打印、被拿去和幻灯片比。这里四条规则保持讲义自己的顺序和措辞，读回来时逐字一致。

**而且对拍是可以不一致的，一旦不一致，原因被指名。** 只能回答「一致」的比较不是比较。在讲义
p.28-29 的程序上——`p = new C(); q = p; x = new X(); y = new Y();`——两种读法在指针关系上
**完全一致**：`p → {o1}`、`q → {o1}`、`x → {o3}`、`y → {o4}`，各四个元组。

**而在持有字符串的字段上两者不一致，而原因是规格自己的。** `pta_run` 的字段单元装的是字段
**装着的值**（p.59 把 `"x"` 放进一个 points-to 集合），而讲义的 `FieldPointsTo` 装的是字段
**指向的对象**，字符串不是对象。所以在讲义 p.57 的程序上，讲义的字段关系是空的，而 `pta_run`
的字段单元是 `{"x"}`，连带着读这个字段的那个变量两者也不一致。这是两份**规格**的事实，不是
其中任何一份的错误——它被报告出来，而不是被归一化掉。

**而且对拍会把两份答案并排打印出来**，因为只打印一个布尔的比较，是读者只能选择相信的东西。

### 讲义自己的污点规则可以跑起来，而且它们在这个引擎里找出了一个真 bug

讲义第三件要理解的事（p.93）是「用 Datalog 做污点分析」，它那一章只有两页（p.90-91）：
EDB 关系 `Source(m)`、`Sink(m, i)`、`Taint(l, t)`，IDB 关系 `TaintFlow(sr, sn, i)`，以及两条
规则。`src/flow/datalog_taint.mbt` 把它们跑起来，并与 `taint_analyze` 在同一个程序上给出的答案
对拍。

**讲义自己的那个三元组被找到了，就在这个讲义自己的程序上。** 安全那份讲义的七语句例子
（p.77）在 p.84 上印着 `TaintFlows: { <3, 7, 0> }`——源调用点、汇调用点、参数下标——而 Datalog
读法推导出的正是这个三元组，两种读法**一致**。

**而且跑讲义自己的规则，在这个工具的引擎里找出了一个真 bug。** 分层排序的循环拿**谓词**的个数
去和**分组**的个数比较——这是两个不同的东西——于是在一个「三个 IDB 谓词、两个分层」的程序上，
循环提前退出，第二个分层**从未被求值**，`TaintFlow` 那条规则根本没跑过。

**这个症状从答案上看不出来**，也正因如此它值得实测而不是猜：程序确实推导出了
`VarPointsTo(s, t3)`——污点数据**确实**到了汇的参数——却从中**没有**推导出任何流。关系是对的、
规则是对的、程序是对的；缺的是一个分层。修法是数分组，而**钉住它的那一行被证明真的会亮**：把 bug
重新放回去，测试套件在三行上变红，文件随后按字节还原。

**而且引擎现在把它的求值顺序暴露出来**，因为顺序是程序的性质而不是求解器内部的性质——看不到
顺序的调用方，无法解释一条什么也没推出来的规则。

### 讲义的第一章被数清楚了，最后两页也被核对过了

讲义第一章是动机（p.5-16）：它印出带工作表的命令式 `Solve(main)`，并问出命令式形式没有回答的
问题。这张清单是**逐页增长的**——p.10 三条、p.11 多一条 points-to 集、p.12 再多一条——到 p.12
一共**五条**；第五条「How to connect PFG nodes and pointers?」印在 p.12 上，很容易漏掉。

**答案不是「声明式形式没有实现细节」。** 在这个工具自己的引擎上实测：声明式形式关掉了讲义五个
问题里的**四个**，留下**一个**——points-to 集的存储方式，正是讲义自己那句「Hash set or bit
vector?」。这个引擎把元组存在一个**哈希集合**里，键是带长度前缀的元组键，所以讲义的问题在这里
被回答成：点名采用了讲义自己给的两个选项中的哪一个。

**而且「顺序」那个问题并没有消失。** 「哪个工作表项先处理」变成「哪个分层先」——同一个问题换了
一顶帽子，而讲义 p.92 的 cons 自己点出了它：「Cannot fully control performance」。这个树已经为此
付过账：0594 找出的分层排序 bug 就是这笔账。

**p.92 是三条优点、两条缺点，其中一条优点在这里并不成立。**「Benefit from off-the-shelf optimized
Datalog engines」对这个树不成立，因为它有自己的引擎——而代价是实测出来的，不是断言出来的：0594
那个分层排序 bug 就是拥有引擎的代价。它被明明白白写成「不成立」，而不是靠沉默暗示。

**而「Restricted expressiveness」在这里是两次拒绝，不是一句含糊的限制**——不安全规则（p.53）和
递归与否定冲突（p.56）都被拒绝，而拒绝会说出是哪条规则、为什么。

**p.93 是三件事，每件都写明做它的那个增量**：语言（0592）、用 Datalog 做指针分析（0593）、用
Datalog 做污点分析（0594）。

### 超图是被**测出来的**，而爆炸超图是被**造出来的**

这一讲是《CFL-Reachability and IFDS》（`15_IFDS.pdf`，南京大学，李月，2021）——174 页，p.3 上是**六章**，
p.174 上写着要理解的三件事：*Understand CFL-Reachability*、*Understand the basic idea of IFDS*、
*Understand what problems can be solved by IFDS*。`src/flow/ifds.mbt` 覆盖它的**第四章**
（p.58-81，超图与流函数）和**第五章的前一半**（p.83-97，爆炸超图与 glue 边）。

**讲义的配方有三步，而这个增量做完的是前两步。** p.52-56 给出这三步：为 P 建一个超图 `G*` 并
定义其边上的流函数；把流函数**变换成表示关系**（图），得到**爆炸超图** `G#`；然后用 `G#` 上的
**tabulation** 把问题化成图可达性来解。让第三步成为答案的定理印在 p.55-56：事实 `d` 属于
`MRPn` **当且仅当** `G#` 上存在一条从 `⟨smain, 0⟩` 到 `⟨n, d⟩` 的**可实现路径**。tabulation 是
0598。

**第四章本来就在这棵树里，所以 0597 是去测量它，而不是再造一份。** 讲义 p.63-65 给每个过程
调用三条边——过程内的 call-to-return-site 边、过程间的 call-to-start 边、过程间的
exit-to-return-site 边——而 `src/flow/icfg.mbt` 建出来的正是这三条（`EdgeKind::CallToReturn`、
`EdgeKind::Call`、`EdgeKind::Ret`）。再造一个超图就是把这个树已经拥有的概念实现第二遍，所以这个
增量去**数**这三条边：`ifds_supergraph_text` 报出调用点与边的种类，`ifds_supergraph_calls` 逐个
调用点地说，从调用点出发的那两条边各在不在。

**而第三条边是分开数的，因为它不从调用点出发。** 讲义那条 exit-to-return-site 边从**被调者的
出口**出发、到**调用者的返回点**结束（p.65），所以在调用点上找不到它的读者，不该因此断定它
不见了——`ifds_supergraph_returns` 在它真正所在的地方逐条报出来。

**缺掉的是表示关系，而它正是讲义的第二步。** p.53 说爆炸超图是「把流函数变换成表示关系（图）」
建出来的，而此前**没有办法**向这棵树要一个「作为图的流函数」。

**而它是讲义自己 p.84 上的那个公式，不是它的改写：**

```
Rf = { (0,0) } U { (0,y) | y in f(EMPTY) } U { (x,y) | y not in f(EMPTY) and y in f({x}) }
```

把这棵树自己的转移 `OUT[B] = gen_B U (IN[B] - kill_B)`（p.48）代进去读，这个公式就是三对：

```
(0 -> 0)   在每个节点上                                 THE GLUE EDGE
(0 -> g)   对每个 g in gen[B]                            常量部分
(x -> x)   对每个既不在 gen[B] 也不在 kill[B] 里的 x      事实活过这个节点
```

而 `ifds_reach_rel` 是**调用** `reaching_gen` 与 `reaching_kill` 得来的，不是重新实现一遍——于是
爆炸超图和传统分析是**同一组转移函数的两种读法**，这正是下一个增量的对拍有意义的原因。

**第三个子句把「被生成的」事实排除在外，而这是公式本身而不是一种取舍。** 讲义 p.85-87 自己
的例子写着：`lambda S.{a}` 的边是 `0->0`、`0->a` 和 `b->b`——**没有** `a->a`。节点生成的事实已经
由常量部分带走了，所以它不再有自己的 `(x,x)` 那一对。

**glue 边是关系的第一个子句，所以开关也在关系上。** p.84 的 `{ (0,0) }` 是 `Rf` 的一个子句，而不是
旁边另加的一条边，于是 `ifds_reach_rel` 把 glue 边作为**参数**收进来——一个不能把东西关掉的
测量就量不了它，而讲义 p.92-96 恰恰是**关于**那个子句的断言。

**而没有它，超图是断开的——这正是讲义自己的失败情形。** 在那十行所钉住的五节点图上实测：
**没有任何一条边离开起点对** `⟨entry, 0⟩`——这个爆炸超图不是「有点不对」，它是**断开的**。
这正是 p.95 那句话：没有 `0->0` 边，「每条边的表示关系就无法连接、无法『拼接』起来……于是 IFDS
无法通过这样断开的表示关系给出正确的解」。

**而有了它，超图就连上了，而且它到达的事实就是分析自己算出的那些。** `(0,0)` 那一对是把零事实
从一个关系带到下一个关系的边，所以下一个关系的常量部分才有零事实可以点燃——这就是「拼接起来」的
意思。实测，每个节点上到达的事实恰好是传统分析的 `IN[n]`：`x@1` 在节点 2，`x@2` 在节点 3 和 4，
`y@3` 在节点 4，而 `x@1` **不在**节点 3，因为节点 2 把它 kill 掉了。

**而这个计数就是算术，写在明处。** 每个节点贡献的是它的关系的成对数乘以它的后继数，于是爆炸
超图带 glue 时有 **14** 条边、不带时 **10** 条：节点 0 贡献 4、节点 1 贡献 3、节点 2 贡献 3、
节点 3 贡献 4、节点 4 贡献 0——而出口节点没有后继，所以 glue 边出现 **4** 次而不是 5 次。

**十一行，每一行都点出自己的幻灯片**，在 `src/flow/ifds_test.mbt` 里——p.58-65 是那三条边，
p.46 与 p.48 是关系与 kill，p.84 是那个公式，p.95 与 p.96 是 glue 边，p.53 是爆炸图的边。

**而这个增量自己的六个缺陷是被测量找出来的，并且被修掉，而不是被钉住。** 最大的一处：初稿把
`(0,0)` 放在关系**外面**，改成在每个节点上放一条 `0->0` **自环**——而自环哪儿也带不动零事实，
于是它建出来的爆炸超图什么也到不了。实测，可达集只有一个点。讲义自己的 p.84 公式把 `(0,0)`
放在关系**里面**，现在代码照公式做。其余五个：`with` 是保留字；一个没被用到的 `facts` 绑定；
逐调用点的边列表用空格分隔，而 `"CallToReturn"` **包含**子串 `"Ret"`，于是找 `"Ret"` 的测试会
**测到错的边**却看不出错；两个当**值**用的 `if` 表达式把自扫描的 `if expression` 那行从 100 顶到了
102；还有一行的期望值是猜的而不是量的。假阳性是要修的，不是要钉的。

### tabulation 被**跑起来**，而且和本仓库已有的答案**对上了**

讲义的第三步（p.52-56）才是把爆炸超图变成答案的那一步：「Q can be solved as graph reachability
problems (find out MRP solutions) via applying Tabulation algorithm on G#」。p.139-140 说这个算法
做什么——「Given an exploded supergraph G#, Tabulation algorithm determines the MRP solution by
finding out all realizable paths starting from ⟨smain, 0⟩」——p.141 印出它的代价：**O(E·D³)**。

`src/flow/ifds_tab.mbt` 就是那个 tabulation，而且它是**过程内**的那个：讲义自己在 p.142-143 上
说了它并不覆盖整个算法。

**而这一版的测量是：它复现出了本仓库已经算出来的分析。** `reaching_out` / `reaching_in` 是传统
的到达定义分析，它们解的是集合上的不动点方程；tabulation **走的是一张图**。两者是**同一组转移
函数的两种读法**，所以必须一致——逐节点、逐事实地一致。实测，一致：`IN[2]` = `{x@1}`、
`IN[3]` = `{x@2}`、`IN[4]` = `{x@2, y@3}`，而 `x@1` **不在**节点 3，因为节点 2 把它 kill 了。

**而 glue 边的效果是**答案**上的差别，这正是讲义自己的断言。** 没有 `(0,0)` 那个子句时，
tabulation 的答案是**空的**：起点只带着零事实、别的什么都没有，而其余每个节点**什么也没有**——
连零事实都没有。同一张图上，传统分析找出三个定义。于是 p.95 那句话是被测出来的，不是被引用的：
「Thus IFDS cannot produce correct solutions via such disconnected representation relations.」

**而讲义自己的上界就印在实测的工作量旁边**，覆盖率也在旁边：E = 14 条边，D = 4 个事实（三个
定义加零事实），于是上界是 14 · 4³ = **896**，而这次行走过了十四条边里的 **8** 条。没走过的那
六条讲的是同一件事：它们的**源**对从未到达——其中三条从入口节点出发、以定义作为源，而没有任何
定义能到达入口，因为这次行走是从入口的零事实开始的。

**五行，每一行都点出自己的幻灯片**，在 `src/flow/ifds_tab_test.mbt` 里——p.139-140 是 tabulation
与对拍，p.92-96 是那个空答案，p.141 是上界，p.140 是可读的渲染。

**而这个增量自己的算术是被测量纠正的**：工作量的那一行初稿写的是走过**十条**边，测量说是
**八条**。

### 可分配性边界是**测出来的**，测的是这棵树本来就有的两个分析

讲义的**第六章**（p.155-172）是 "Understanding the Distributivity of IFDS"，p.156-157 问两个
问题：*"Can we do constant propagation using IFDS?"* 和 *"Can we do pointer analysis using IFDS?"*

**而判据就是讲义自己的代数式，p.158：`F(x ^ y) = F(x) ^ F(y)`。** 所以问题不是"这个迁移函数是不是
读了两个名字"，而是"输出是不是各事实单独产生的输出的并"。`src/flow/ifds_distrib.mbt` 测的就是这个，
测的对象是**这棵树自己的**常量传播（`cprop.mbt`）和指针分析（`pta.mbt`）。

**讲义的规则，p.162，原文：**

> Given a statement S, besides S itself, if we need to consider multiple input data facts to create
> correct outputs, then the analysis is not distributive and should not be expressed in IFDS.

**而讲义自己的例子不可分配——这是测出来的。** `z = x + y`，其中 `x=2`、`y=3`：`z` 定义出的值是
**5**，而两个事实各自单独产生的输出的并是 **⊥**。报告读作
`reads=2 z:all=5 one=⊥ distributes=false`。

**是 `⊥` 而不是 `NAC`，这一点值得写出来。** 只知道 `x` 时，`x + y` 不是"不是常量"——它是"这里还没
算出任何东西"，而 `⊥` 吸收。两者是不同的答案。

**而讲义自己更难的那个问题，p.164，在这里有答案。** *"think about whether we could do linear
constant propagation, e.g., y = 2x + 3, or copy constant propagation, e.g., x = 2, y = x, using
IFDS-style analysis?"* **两者都能**，而测量的原因也正是这个：这两条语句各只读**一个**事实，所以
"只给这个事实时的输出"**就是**输出——线性那条是 `reads=1 y:all=9 one=9 distributes=true`。

**而指针分析这一半，是讲义 p.172 的结论，被写成一个可执行的问题。** 讲义说，要在 IFDS 里得到
alias 信息，"we need to consider multiple input data facts, x and y"。在讲义自己的程序上测
（`x = new T; y = x; x.f = x; z = y.f`）：关系 `alias(x,y)` 在整个状态上成立，而在**任何**单事实
状态上都不成立：`alias(x,y)=true facts=4 one=false distributes=false`。

**而对照组就在同一行里，因为一个只会说"否"的测试并没有在测量。** `alias(x,x)` **是**一个单事实的
事实，同一个函数在同一个状态上这么说：`alias(x,x)=true facts=4 one=true distributes=true`。

**而 `z` 的答案跟着 alias 关系走。** 把讲义程序里的**一行**改掉——`y = x` 变成 `y = new U`——
`z` 就指向**空**，而不是指向新对象，同时 `alias(x,y)` 从真变假。这就是讲义 p.171 那句话的测量：
输出恰好在关系成立时才是对的，而这个关系是关于**两个**变量的事实。

**而 load 本身就需要两个事实，这是 p.171 那句话按讲义自己的说法。** load `z = y.f` 在整个状态上
给出 `{o1}`，从任何单个事实出发给出 `{}`，所以单事实输出的并不是输出：
`load(y.f)={o1} facts=4 one={} distributes=false`。

**八行，每行写明自己的幻灯片**，在 `src/flow/ifds_distrib_test.mbt` —— p.158-163 是讲义的例子，
p.164 是讲义自己更难的问题，p.162 是规则的边界，p.165-172 是指针程序。

**而这不是这棵树的那条"合流"（confluence）行。** `cprop_intra_test.mbt` 钉的是**另一份**讲义的
合流——`F(X meet Y) != F(X) meet F(Y)`，在**格的 meet** 上，那是关于格的一句话。这里测的是
**数据事实**上的可分配性，那是关于迁移函数的一句话。两个问题，两行，谁也不借用谁的名字。

### CFL 可达性是**跑起来的**，跑在这棵树自己的超图上

讲义的 **p.24-42** 是 "CFL-Reachability"，而 p.174 把 *Understand CFL-Reachability* 列为这份
讲义要理解的三件事之一。

**而讲义自己的定义，p.24，原文：**

> A path is considered to connect two nodes A and B, or B is reachable from A, only if the
> concatenation of the labels on the edges of the path is a word in a specified context-free
> language.

**而讲义自己的标号规则，p.27，原文：**

> Every right parenthesis ")i" is balanced by a preceding left parenthesis "(i", but the converse
> needs not hold. For each call site i, label its call edge "(i" and return edge ")i". Label all
> other edges with symbol "e"

**而 `src/flow/cfl.mbt` 就是这条规则，作用在这棵树**已经有的**那些边上。** 调用边是 `(i`，返回边
是 `)i`，其余都是 `e`——而那个 `i` 是图自己调用点清单里的下标，所以一条边和它的搭档带同一个数字，
是因为它们来自同一个地方。

**而识别器就是那个文法，p.34-38，从左往右读。** 讲义的语言里有 `realizable` 和 `matched`；识别器
维护一个未匹配左括号栈，并拒绝任何不闭合最内层那个的 `)i`。由讲义自己的例子裁决：p.29 的路径
`(1 (2 e )2 )1 (3` 是可实现的，尽管它**并不平衡**——这就是 p.27 那句"the converse needs not
hold"——p.39 讲义自己那份推导 `e e (1 (2 e e e )2 )1 (3 (4 e` 出于同样的理由可实现，p.41 的
`e(1eee)1e` 在这个语言里，而 p.42 的 `e(1eee)1e(2eee)1` 不在，因为它最后那个
`)1` 闭合的是还开着的那个 `(2`。

**而测量是落在这棵树自己的超图上的，而且不是零。** 一个被两处调用的函数有**一个**值退出和
**两条**返回边，所以图里存在这样一条路径：经一个调用进入被调函数，再经另一个调用的返回边离开。
测出来，在一个三函数程序上，见证路径的词是 `e (2 e (0 e )1`：这条路径经调用点 2 进入 `caller`、
经调用点 0 进入 `leaf`，再从调用点 1 的返回边离开——而栈顶是调用点 0，所以那个 `)1` 闭合错了
括号。

**而这个定义的代价是按**点对**数的，因为 p.24 讲的就是点对。** 图自己的连接有 **82** 条；语言
保留 **57** 条；**25** 条被丢掉。被丢掉的每一条，都是图里存在、却不是一次调用序列的连接。

**而这正是 0599 与 0600 相接的地方。** 这棵树的超图是**可分配**的那一个——它有 call-to-return
边，而那正是可分配性买到的东西——而 CFL 的表述并不需要这条边。有它的代价在这里看得见：超图里
存着不是调用序列的路径，而把它们排除掉的正是 CFL 的定义。

**八行，每行写明自己的幻灯片**，在 `src/flow/cfl_test.mbt` —— p.29 与 p.27 是识别器，p.39、p.41
与 p.42 是三条归属行，p.27 是对这棵树自己的图的标号，p.24 是见证路径与点对计数。

### 而且这个分析器会说明自己是 **SOUND**、**SOUNDY** 还是 **UNSOUND**

这一讲是《Soundiness》（`16_Soundiness.pdf`，南京大学，李樾、谭添，2021 秋季），p.14 给出三种裁决——而它们的区别在于
缺口的**成因**，不在于缺口的大小：

> A soundy analysis aims to capture all dynamic behaviors with certain hard language features
> unsoundly handled within reason
> A sound analysis requires to capture all dynamic behaviors
> An unsound analysis deliberately ignores certain behaviors in its design for better
> efficiency, precision or accessibility

**而且裁决是推导出来的，不是写死的。** 每个家族声明自己的**排除项**以及每一项的成因，裁决由这些
成因算出——所以裁决不可能与它所概括的契约脱节。没有排除项的家族是 **sound**；排除项全部由分析器
无法建模的硬语言特性造成的家族是 **soundy**；只要有**一项**故意的排除项，家族就是 **unsound**，
无论它还带多少硬特性。

**在这十八个家族上实测**，而这些数字由 `check_family_roster.ps1` 从源码推导出来，并在
`_verify/release.ps1` 里钉住：

    sound=0  soundy=15  unsound=3

**而且那三处故意的处理是被点名的**，因为这份讲义的 p.10 正是这一节要回应的抱怨——「在论文的
实现/评测部分里，对硬语言特性的处理通常被略去，或只是一笔带过」，而且「对专家来说，要解释分析
结果（这个分析有多 sound、多快、多精确）仍然很难，除非清楚地说明它对那些重要的硬语言特性是怎样
处理的」：

| 排除项 | 家族 | 分析器选择不去做的事 |
|---|---|---|
| `X-ARG-TYPE-NAMED-ARITY` | MSA-007 ArgTypeMismatch | **具名调用**的实参个数不检查——这是一处故意的宽松，因为另一种做法会产生误报 |
| `X-OP-PIPE-EXEMPT` | MSA-008 OperatorMismatch | **管道运算符**与正则匹配的操作数被豁免 |
| `X-NOSEC-REALITY` | MSA-012 StaleNosec | 被 `// nosec` 静默掉的那条发现被**移除**，而它本来是否真实从不再核对 |

**而且 `--explain` 会打印它**，逐个家族地、也在整份名册上打印：裁决，以及每一项排除及其成因。
所以「这个工具有多 sound」这个问题的答案是一条命令，而不是论文里的一段话。

**而整个分析作为整体是 `unsound`**——这是讲义 p.6 的答案，是实测出来的而不是抄下来的：「能对
真实世界的程序做出一个完全 sound 的分析吗？」不能，而说出这一点的数字是**十八个家族里的三个**，
每一个都有一个被点名的理由。

### 而那些以前被丢掉的跨文件签名，现在读进来了

同一份讲义的**第二章**是《Hard Language Feature: Java Reflection》，它的 p.32 用一句话点出
问题：

> Problem: Reflection targets cannot be resolved if the string values are statically unknown

p.35 给出答案：

> When string arguments cannot be resolved statically, infer the reflective targets at their
> usage points!

**`.mbti` 就是另一个包的接口**，这个分析器读它，是为了知道跨包边界上存在哪些名字。它**没有**
留下的是**参数表**。这一行

    pub fn action_mask_to_action_vec(UInt) -> Array[Action]

明确写着这个被调用者收几个实参、实参是什么类型——而读取器把参数表解析出来之后**丢掉了**，只留下
整行提到的那**一组**类型名，而一组类型名说不出哪个参数是哪个类型。

**丢掉它的那句话是错的**，而且它在源码里被当作事实写着：*「a `.mbti` gives us the NAME,
never the parameter list」*。接口给的就是参数表。现在 `src/core/iface_sig.mbt` 装着它，
`src/moonfiles/moonfiles.mbt` 保留它，而类型透镜会问那张表：它查不了的那个被调用者，是否有一个
**形状已知的靶子**。

**在八棵树上实测**，而第一个数字正是这一增量的要点——靶子一直是可以解析的：

| 讲义 p.40 的那一对 | 数量 |
|---|---|
| 跨文件调用中，被调用者的 `.mbti` 声明了签名的数量 | **2,943** |
| 其中声明的 arity 与该调用的实参个数一致的数量 | **2,282** |

**而那 661 个不一致的不是算错了——它是对这张表的一个警告。** 接口表是**扁平的**：`.repos` 下的
每个 `.mbti` 都被并进同一张表，而 `.mbti` 里的名字是不带限定的，所以一个包里声明的名字可以匹配
另一个包里的调用。实测：`moonbit_image` **自己没有任何** `.mbti`，它的 74 个靶子里有 **73 个**
不一致；而凡是调用有被声明到的语料，一致率落在 **63.6%**（`async`）到 **82.6%**
（`moonbit_core`）之间——`proton` 80.4%、`moonbit_labeler` 78.2%、`moui` 77.7%。

**所以这次推断是被计数的，而不是被执行的**——这不是回避，而是讲义 p.39 的教训：*「The reflective
target method at line 175 must have one parameter and its declared type must be
FrameworkCommandInterpreter or its sub/supertypes」*——推断出来的靶子必须由它的**类型**来约束，
而不是只靠**名字**；而这张表手里只有名字。两个计数由 `--metrics` 打印，发布门禁把它们对着
分析器自己打印的那一行钉住。

### 手写建模的那部分原生接口，现在拿声明出来的那部分量一量

同一讲的**第三**章是*Hard Language Feature: Native Code*，p.57 用两行写下当前的做法：

> Current practice
> Manually models the critical native code

p.58-59 给出它存在的原因：

> For efficiency, arraycopy() is implemented in native code

p.60-61 给出**另一种**建模——同样的行为用高级语言写出来，而不是手写建模：

> An alternative modeling
> System.arraycopy(src, sp, dest, dp, ln);
> Java
> for(int i = 0; i < ln; i++)
> dest[dp+i] = src[sp+i];

p.62 给出分析器自己的视角，p.63 点出更新的读法：

> Recent work
> Identifying Java Calls in Native Code via Binary Scanning (ISSTA 2020)

**本项目做的正是第一件事**，而且它带着一个数字：`src/core/builtin_methods.mbt` 是一张
**1,344** 个 `Type::method` 名字、覆盖 **40** 个内建类型的表，由
`tools/gen_builtin_methods.ps1` 生成，并盖上它最后一次读取时对应的工具链版本。

**0604 拿接口声明出来的那部分来量它**——就是讲义 p.60-61 的那种替代建模，落到本项目
自己的问题上。分析器现在读目标**自己的** `.mbti`（在**同一次**遍历里，不是第二次遍历），
问它们为那四十个类型声明了什么。

| 讲义 p.57 的问题 | declared | covered | missing |
|---|---|---|---|
| `moonbit_core`——标准库自己 | **1,155** | **1,075** | **80** |
| `async` | 10 | 0 | 10 |
| 其余五个语料 | 0 | 0 | 0 |
| 本仓库自己 | 0 | 0 | 0 |
| **八棵树** | **1,165** | **1,075** | **90** |

**而这些零是测量结果，不是测量本身的漏洞。** 手写的那张表是**标准库**的接口面，用户
自己的包不会为它声明任何方法——所以只有那棵**就是**标准库的树才对此说得上话。`async`
是另一棵说得上话的树：它为某个内建类型（`Buffer`）声明了十个方法，而手写的那张表
一个也没有。

**这 80 个是假阳性的方向，而它们今天不会真的报出来。** 工具链声明了、手写表里没有的
名字，是一个等着出现的假阳性——**前提是接口不在那儿替它兜底**。在 `moonbit_core` 上
实测：这 80 个里**零**个出现在 `undefined function` 的发现里，因为 `.mbti` 把它们解析了。
所以这是个**兜底**的缺口，而讲义 p.60-61 的那种替代建模正是能把它彻底关掉的方向。

**另一个方向是 269**——手写表里有、而 `moonbit_core` 不再声明的名字。那是漏报的方向，
而表头自己说了它是故意接受的：留着一个工具链已经删掉的名字是漏报，丢掉一个工具链还
有的名字则是假阳性。

**表落后一个工具链世代，这一条也是量出来的——而且这个测量在第一次量完之后**动过**。** 表上盖的是
`moon 0.1.20261016`；这台机器上的工具链是 `moon 0.1.20261117`，它锁定的那个 core 声明了
**1,155** 个、缺 **80** 个——这台机器上工具链自带的 core 树量出来的是同一组数。一个工具链
世代之前的那个锁定值声明的是 **1,123** 个、缺 **47** 个。所以缺口比表上的戳暗示的**更大**，
而且这个测量在两代工具链之间**是会动的**——早先「它不动」那个说法被这一增量自己的测量
推翻了，就在这里改掉。

**所以 0604 只公布覆盖面，不重建那张表。** 重建它是一次会改变分析器**发现了什么**的
发布——这张表只会压制，所以它每多一个名字就少一条报告——那属于一次要重新量七个语料的
发布，而不是一个只做测量的增量。

### CFG 底下还有一层：基本块

`src/flow/bb.mbt` 把一个 CFG 拆成**基本块**，再在基本块上建控制流图——也就是 CFG 通常
被画在其上的那一层。它对齐的那份讲义（南京大学 2026 秋季《Intermediate
Representation》）印了一份完整的实例，并把两个问题点名成可执行的问题：*「How to build
basic blocks on top of IR」*和*「How to construct control flow graphs on top of BBs?」*。
它那十二条指令连同 **leaders** 和**基本块**都是印出来的，所以这一层是拿印出来的东西
对拍，而不是拿自己的输出对拍。

讲义里的两条指令在 MoonBit 里没有对应的语句——一条无条件 `goto`，一条离开整个程序的
`return`——所以那份程序是手工搭成图的，而且搭成本仓库自己的构造器产出的形状（节点从后
往前分配，所以源码序是被**验证**的而不是被假定的）。同一个形状随后又用 `cfg_of` 从真正
的 MoonBit 语句再搭一遍，因为只对手工图有效的层，等于没有证明自己有效。

块图的**形状**和节点图一样——一个计数、一个后继关系、一个前驱关系——所以现成的求解器
不用写第二个就能跑在它上面，其中一行测试把同一个可达性分析在两张图上都跑一遍，并要求
两者一致。讲义里的 Entry 和 Exit 不是基本块：它说这两个节点「do not correspond to
executable IR」，所以它们被并排放在块列表旁边而不是混进去。`break` 是跳出**循环**而不是
跳出**函数**，而图分不出这两种 `Stop`，所以构造器没能忠实转换的语句计数被一并带出来，
调用方要先看它——和死存储家族的做法一样。

### 基本块底下还有一层：规则本来就是写在三地址码上的

`src/flow/ir.mbt` 是同一份讲义陈述那些规则时所用的**三地址码**。它不是一堆指令，而是一门
有语法的语言，而讲义把语法印出来了：一条指令的右边最多一个运算符，所以 `c = a + b + 3` 降级成
`t1 = a + b` 再 `c = t1 + 3`；一条指令最多三个地址；地址恰好三种——**名字**、**常量**、
**编译器生成的临时变量**。那六个常见形式是 `x = y`、`x = uop y`、`x = y bop z`、`goto L`、
`if x goto L`、`if x rop y goto L`。

`src/flow/ir_cfg.mbt` 随后把讲义的 **leader 规则**、**边规则**和 **Entry/Exit** 直接作用在
这样一条指令列表上——**完全不做翻译**。上一层是不得不翻译的，因为讲义把规则写在三地址码上，
而本仓库的图是语句图，所以那份翻译只能被相信、无法被检验。现在两条路径在讲义自己的程序上
互相对拍：同样的 leaders、同样的块、同样的边、同样的入口、同样的出口。这和两个求解器互相对拍
是同一个形状。

三地址码路径产出的是语句路径产出的**同一个 `Bb` 类型**——这是故意的：块图是一件事、一个定义，
两个可能对「块是什么」有不同看法的结构，等于对「块」有两个定义。

两个扩展项是明着标出来的，不是偷偷塞进去的：讲义的 IR 根本没有调用形式（这正是它把
`x = input` 写成从名为 `input` 的地址拷贝的原因），而它那「六个常见形式」里也没有 `return`，
尽管它自己的程序最后一条就是 `return`。

讲义自己那十二条指令，严格说**并不是**三地址码：`(9) c = 2a - b` 的右边有两个运算符，而 `2a`
不属于那三种地址之一。夹具原样保留讲义的文本，所以讲义印出来的块就是代码产出的块，并且有一行
测试把这件事写成话——一个「修正」过实例的夹具，检验的就不是讲义印出来的东西了。

`src/flow/laws_test.mbt` 把两个有限格的每一个元素都枚举出来，检查五条格律，以及传递
函数的**单调性**——不动点定理会用到的那个前提，也是一个格的三条闭包本身保证不了的那条
性质。points-to 表的格也是同样检查的。

### 还有讲义页脚上印的那个箭头：3AC -> SSA

`src/flow/ssa.mbt` 是同一份讲义第五节定义的**静态单赋值**形式。讲义用几句话陈述它的规则——「所有 SSA
里的赋值都是给名字互不相同的变量」「给每个定义一个新鲜的名字」「把这个新鲜的名字传播给后面的使用」
「每个变量恰好一个定义」——而页脚印着它讲的那个箭头：`3AC -> SSA`。

讲义自己的那张图就是检验。它把 `if e` 分到 `x₀ = 0` 和 `x₁ = 1`，两者汇到一个节点，那个节点里是
`y = x + 7`——`x` 被**红圈**标出来，因为那一页问的就是这件事：「如果一个变量的使用落在控制流汇合处
怎么办？」答案就是下一页引入的合并算子：`x₂ = ∅(x₀,x₁)`，而且「∅(x₀,x₁) 在控制流经过条件的真分支时取
x₀ 的值，否则取 x₁ 的值」。`src/flow/ssa_test.mbt` 把那张图变成一个程序、降级成三地址码，然后要求结果
与那张图**逐条指令**相同：

```
if e goto L1
goto L2
x₀ = 0
goto L3
x₁ = 1
x₂ = ∅(x₀,x₁)
y = x₂ + 7
```

讲义留白的两件事是**量出来的**，不是凭口味定的。它把汇合节点画成一个有**两条入边**的节点，说 φ 函数
「在汇合节点上选取各个值」——但一个变量的两个定义相遇的地方并不是那个地方，而是**支配边界**，
`src/flow/dom.mbt` 算的就是它。而那张图把 `y` 画成没有下标、`x` 却有三个，所以恰好只有一个定义的变量
保留它的裸名字。

**讲义自己那条代价说法，实测。** 《Intermediate Representation》（`2_IR.pdf`）那一讲的 p.37 说「SSA 可能引入太多变量和 φ 函数」「在翻译成机器码时可能引入效率
问题（因为拷贝操作）」——两条说法都不带数字。在讲义自己那个十二条指令的程序上：**8** 个变量变成 **16**
个版本，出现 **8** 个 φ 函数，去掉它们需要 **16** 条拷贝。在本项目自己的源码上——263 个文件、1,437 个
函数、9,222 条三地址码指令——同一个测量给出 **1,171** 个变量变成 **2,808** 个版本、**975** 个 φ 函数、
**2,408** 条拷贝。这条说法不是修辞。

这个测量是扫描器的一个模式，`--ssa-cost`，它打印一行：

```
SSA-COST	files=263	unreadable=0	functions=1437	converted=5	partial=1432	declined=6541	…
```

它把**覆盖率**和数字印在一起，因为没有覆盖率的数字只是一半个数字：读了哪些文件、量了多少个函数、
以及 lowering 放弃了多少条语句（6,541 条——三地址码那层把它懂的语句转掉，其余的计数）。发布门禁把这一行
钉住，所以下一个动它的增量必须**故意**去动那个钉子。
## 验证

```bash
moon check --target all --deny-warn   # 0 错 0 警（js / native / wasm / wasm-gc）
moon test --deny-warn                # wasm 1807/1807；js 与 wasm-gc 1642/1642
moon run src/cli                     # 程序 demo + 文件种类 demo + 样例机器审计
```

`--deny-warn` 是刻意的：不加它，就没有任何东西强制「0 警」这个说法——一次告警回归会静悄悄

### 这三项转移是被要求做的什么

置信度轴、稳定的家族 id 和 `nosec` 不是这个项目自己发明的。它们是**一份需求文档里的
三行要求**——那份文档在本仓库的**上一级目录**：`bandit_review.md`，一份对 PyCQA
`bandit` 的评审，读于 **2026-10-27** 的工作树。那份文档在这里**不会被改**：一份被改成
迎合实现的需求文档，就不再是需求了。

| 行 | 它要求什么 | 实现它的文件 |
|---|---|---|
| 1 | 每个发现一条**置信度**轴，与严重度并列 | `src/core/core.mbt`、`src/report/report.mbt`、`src/jsoncli/main.mbt` |
| 2 | **稳定的家族 id**，以及一个被检查的 profile | `src/core/core.mbt`、`src/sa/profile.mbt` |
| 3 | **`nosec`**，包括那条「抑制没压住任何东西」的警告 | `src/sa/profile.mbt`、`src/sa/main.mbt` |

第 3 行落在**别的地方**，和评审预测的不一样。评审把它放在 `parser.mbt` 的 skip
机制里，而 parser 并不参与：一条什么都没压住的抑制，是关于**最终**发现集合的事实，而
parser 层的 skip 跑在产出那个集合的镜头**之前**。推理过程、评审给那一行自己钉的
pin（0507 按 settle 自己的话把它反转了），以及那份有日期的状态栏，都在
`_verify/NARRATIVE.md` §0514。

**这份地图是被检查的，不是被断言的。** `_verify/check_transfer_scope.ps1` 点名那份
文档、逐字引用那三行，并把 §0514 地图里的每个 `file:line` 对着这棵树解析一遍——文件
在，而且那一行还带着那个符号。它的 `-SelfTest` 会往一份副本里为「这道门禁可能不再
守住的每一种方式”注入一种缺陷，并要求每一种都被抓到。**全部被抓到**，而且门禁会打印出
到底有几种。

这份名册是**被检查的，不是被断言的**：一个在磁盘上存在、却不在名册里的变异门**永远不会跑**，
而一个不会跑的变异门和一个跑绿了的变异门长得一模一样。`_verify/check_gate_roster.ps1`
把两份名册**双向**比对；它的 `-SelfTest` 往 `_verify` 的**副本**里注入十种缺陷——名册没
列的变异门、名册列了却不在磁盘上的变异门、脱离共享 harness 的变异门、被删掉的 harness
保证、harness 里的 `--filter`、harness 头部过时的计数、一条没有指明项目根目录的 moon
调用、一道发布门禁不会跑的 `check_*` 门禁、一道声明了 `-SelfTest` 却从不使用它的
`check_*` 门禁，以及一道既没有开关也没有说明理由的 `check_*` 门禁——并要求每一种都被
抓到。**十种
全部被抓到。**

而且同一份名册现在也管起了 **`check_*` 门禁**，此前它不管。一道在磁盘上、却没被发布门禁
点名的 `check_*.ps1`**永远不会跑**——它在磁盘上，名字像一道门禁，而一次发布运行会把每道
门禁都报成绿的。而一道声明了 `-SelfTest` 却从不使用它的 `check_*.ps1`，就是一个什么也
选不中的开关：它看起来像这道门禁能被证明会变红，而它不能。2026-11-20 实测：
`_verify/check_prove_contracts.ps1` 声明了 `param([switch]$SelfTest)`，然后再也没提过
`$SelfTest`——**而这道门禁的全部主题，恰恰是一个从未被证明会变红的红**。所以现在每一道
`check_*` 门禁都被算清楚：它要么带一个**活的** `-SelfTest`——既被声明，又被正文读取，
而且只在**代码行**上计数，这样关于这个开关的散文没法把一个死开关装成活的——要么它就在
注释里写明自己为什么不带这个开关。**每一道都算清楚了。**

**发到注册表的东西也被检查。** 打包哪些文件由 `.moonignore` 决定，而一份没人验证过的
意图清单就是一句注释。`_verify/check_package_contents.ps1` 跑 `moon package --list`
——和 `moon publish` 用的是同一条命令——并断言：碎屑**不在**（提交信息草稿、扫描产物、
凭据、门禁记录、remeasure 转储），证据**在**（89 道变异门及其 harness、settle 脚本、
叙述、名册门，以及读者会被引去的那几份文档），并且每一个被 git 跟踪的文件都发得出去——**除了那些
故意写坏的 fixture**：每个家族都要靠一个 `.mbt` 文件来证明自己会触发，它们是门禁的**输入**，不是
工具自己的源码。把它们发出去的后果是，发布出去的 0.5.1 **过不了它自己的自检**：跟它一起发布的
那个分析器读完了包里全部 304 个源文件，报出 **15** 条可执行的发现，每一条都是某个 fixture 故意
带上的缺陷。所以门禁现在**从另一个方向**断言它们不在包里——这条例外是一条规则，不是一个洞。
**两个方向都已被证明会变红**：把 `COMMIT_*.md` 那条规则注释掉，包里就多出 23 份草稿，
门禁失败；把 `_verify/NARRATIVE.md` 排除掉，叙述就没了，门禁也失败；
把 fixture 那两条规则去掉，24 个 fixture 就回到包里，门禁失败。

**通知不是错误，标签就是这么说的。** 一条声明过的范围限制——「match expression is outside
the analyzed subset; it was read but not analysed」——渲染成 **`notice:`**，绝不是 `error:`：
它说的是分析器读到了什么，不是它读到的代码有什么毛病。`FParse` 是一个家族、两种含义，
两者由一个判定 `Report::is_notice` 分开，而渲染器、SUMMARY 里的 `actionable` 计数、
mermaid 图和 JSON 桥全都走它——所以标签和数字不可能互相打架。
`_verify/check_notice_labels.ps1` 检查渲染出来的输出、用工具自己的消息跑遍四条产出路径，
并在源码里守住标记的约定。**它的两半都已被证明会变红**：把范围限制又标成 `error:` 会失败，
从某条跳过消息里去掉标记也会失败。

两个开关会改变它的行为：`-SkipMutations` 跑除变异门以外的一切；`-SelfTest` 拿一个失败
的、一个抛异常的、一个通过的函数体去考验门禁自己的 stage 函数。**一道从没被证明会变红的
防护不是防护**，而这里就是证明它的地方。

### 形式验证（`moon prove`）

`src/core` 是证明对象：`src/core/moon.pkg` 里 `proof_enabled = true`，用来启用 MoonBit
2026 的实验性形式验证；`src/core/core_proof.mbtp` 是逻辑侧——谓词 + **19 条引理**。
这 19 条引理在 2026-10-03 实测为 **21/21 个目标 VALID**（unsat），每一个都用 cvc5
机器验证过。

> **这条命令今天跑不绿，原因已量过。** `moon prove src/core` 报
> `unbound type symbol 'array'`——**不是** `'map'`。生成的 Why3 文件自己声明了这两个
> 抽象类型：`type array 'a1` 在第 136 行，`type map 'a1  'a2` 在第 138 行。它们是**先使用、后声明**的：
> `array` 用在第 20 行（`IfaceSig`），`map` 用在第 27 行（`IfaceSymTab`）——而 Why3 要求
> 一个类型先声明再使用。于是文件加载不了，什么也没被证明：`0 of 1 packages proved`，
> `0 goals proved`。
>
> **原因被重新量过了，而这一段原先给出的解释是错的。** 它把责任推给工具链的证明前导
> 库。下面的实验推翻了它，也推翻了那个解释附带的建议——说 `IfaceSymTab` 必须移出证明
> 范围，而那会改本包的公开 API，所以是版本线上的决定。**要弄清这件事，不动公开 API
> 也行。**
>
> **实验。** 只把 `array` 的声明提上去，错误就往前走了一步：变成第 28 行的
> `unbound type symbol 'map'`。两个都提上去，`why3` 就把文件加载了，生成 21 个 VC 并以
> 0 退出——这 21 个里 cvc5 对 20 个回答 `unsat`，`severity_taxonomy_holds` 回答
> `unknown (incomplete)`（2026-11-20 实测，core 0.10.21+06da1ed44；把时限放到 300 秒
> 也一样）。**卡住引理的不是本包源码，而是两条声明被写出来的顺序，那是工具链要修的。**
> `_verify/check_prove_status.ps1` 会跑证明器，把这一段、它的英文孪生、工作区技能文件和
> 旁边那道门禁，都钉在证明器今天报出来的东西上。
>
> 还有两处 `#proof_pure` 标注是**假的**：`path_tail` 和 `unqualified` 的函数体会
> 构造 `StringBuilder`，证明器不认（错误 4207）。一处假标注就让整个文件停止证明，
> 而这两处都是 2026-10-09 加上的。它们已被移除，并且 `_verify/check_prove_contracts.ps1`
> 现在会在发布门禁里拦住任何「证明器不认的 `#proof_pure` 函数体」。

## 参与开发

1. Fork 仓库并建一个特性分支。
2. 给新功能加测试。
3. 把发布门禁跑绿：

   ```bash
   powershell -NoProfile -ExecutionPolicy Bypass -File _verify\release.ps1
   ```

4. 提一个 pull request。

这道门禁不是装饰：它会跑 **89 道变异门**，每一道都改源码、要求一个测试变红、
并证明恢复是逐字节一致的。
**519** 个存活变异里，**477** 个预期被杀；其中 **400 个**还点名了必须变红的是哪个测试，
所以门禁日志说的是**哪个**测试在守着这道防线，而不只是「有东西红了」。
这三个数字都由 README 门禁**从门禁源码自己算出来**——没有被检查过的公开数字，
是会悄悄消失的。

这 88 道门里有四道**从 0570 和 0571 起就是红的**——不是失败，而是**根本没跑**。每一道变异门
都锚在源码某处的原文上；0570 教会了 walker 走 `catch`/`noraise` 分支的 guard，0571 又给 id
映射表加了两个族，两者都改了那些地方却没有改锚点，于是预检直接报
*「N pattern(s) absent. No suite was run.」*。**0.4.47 就是在本地发布门禁为红的情况下发布的**
——这一点是对每一个发布 tag 实测出来的，不是猜的：从 v0.4.30 到 v0.4.46 这四道门都是绿的，
v0.4.47 是红的。现在它们是**重新指向当前代码，而不是退役**——它们测的代码还活着，每个变异
仍然必须能变红——并且四道门各自实测为绿，每一次恢复都逐字节一致。
